# 011. Долги, интервальное повторение, проверка пунктов эталона, итоговая приёмка

Статус: одобрена 03.11.2026 (все вопросы — А, §14). Спринт 11 (roadmap §11), последний.

## 1. Цель

Закрыть долги спринтов 1–10, взять из «После MVP» только то, что усиливает систему и исследовательскую часть,
и подготовить итоговую приёмку всего проекта одним проходом автора. Одним предложением: **первое голосовое
честно предупреждает, что распознавание ещё готовится; повторение тем идёт по интервалам (SM-2) — тема,
ответ по которой был хорошим, возвращается через день, неделю, месяц, а не забывается навсегда; разбор
ответа предупреждает, если сам пункт эталона, похоже, неверен; а в конце — один итоговый чеклист на весь
проект.** Всё, что касается пользователя, — и в боте, и в вебе.

## 4. Подсказка для первого голосового (приоритет 1)

### 4.1. Что видит пользователь

Чистая установка, воркер ещё качает whisper `small` (~0,5 ГБ). Человек отвечает голосом:
- **бот:** статус «🎧 Готовлю распознавание — первый раз это пара минут, потом быстро…» вместо «🎧 Распознаю
  речь…». Дальше как обычно: «🧠 Оцениваю ответ…» → оценка;
- **веб:** тот же текст в статусе под ответом.

Модель уже скачана — всё как сейчас. Скачать не удалось (нет интернета при первом запуске) — тот же текст;
воркер пробует скачать при самом распознавании (как сейчас), при сбое — обычное «не удалось распознать,
ответьте текстом».

### 4.2. Как устроено

- Воркер при старте ставит ключ Redis `asr:model:{модель}` = `downloading`, после `prefetch` — `ready` или
  `failed` (без TTL; при следующем старте воркера ставится заново). Первая успешная расшифровка тоже ставит
  `ready` — на случай, если `prefetch` упал, а потом модель скачалась сама.
- API при приёме голосового читает ключ и кладёт в ответ `asr_ready: bool` (ключа нет = `false`: воркер ещё не
  стартовал). Бот и веб выбирают текст статуса по этому полю. Отдельного запроса нет — приём ответа остаётся
  ≤ 2 с (BOT-4).

### 4.3. API

`POST /sessions/{id}/questions/{qid}/answer/voice` → `202` `{"answer_id", "status", "asr_ready": true}`.
Текстовый ответ поле не возвращает (`null`, исключается из JSON).

## 5. Интервальное повторение SM-2 (приоритет 2)

### 5.1. Что не так сейчас

PRG-2: тема слабая, если среднее последних попыток < 60. `/repeat` берёт только слабые темы и «мало данных с
низким баллом». Тема, на которую человек один раз ответил на 75, больше не повторяется никогда — хотя через
месяц он её забудет. Именно это и решает интервальное повторение.

### 5.2. Что видит пользователь

- **Прогресс** (`/progress` в боте, страница «Прогресс» в вебе): у каждой темы, кроме статуса и среднего,
  строка «повторить: сейчас / завтра / через 6 дн. / 14.11». Слабые темы — «сейчас», как и раньше.
- **`/repeat`** и кнопка «Повторить» в вебе: берёт темы, у которых подошёл срок, — сначала с меньшим баллом.
  Слабые темы подходят сразу, поэтому для них поведение не меняется. Новое — «в порядке» тоже возвращаются,
  когда подошёл срок.
- **Сроков нет** (всё повторено недавно и хорошо): см. вопрос 1.

### 5.3. Алгоритм (`packages/core`, чистая функция, без LLM)

SM-2 (Wozniak, 1990) с двумя поправками под систему:

1. **Балл → качество 0–5:** ≥ 90 → 5, ≥ 75 → 4, ≥ 60 → 3, ≥ 40 → 2, ≥ 20 → 1, иначе 0. Порог «сдал» (3) = 60 —
   тот же, что у слабой темы в PRG-2, чтобы статусы и сроки не спорили.
2. **Провал — повторить сразу, а не завтра:** при качестве < 3 повторений = 0, интервал = 0 дней (в
   классическом SM-2 — 1 день). Так слабые темы, как и сейчас, сразу попадают в `/repeat`.

Остальное — как в SM-2: интервалы 1 день, 6 дней, дальше × EF; EF стартует с 2,5, меняется после каждой
попытки по формуле SM-2, не ниже 1,3. Срок = время последней попытки + интервал.

Состояние **не накапливается, а пересчитывается из истории**: `recompute_topic` уже читает все попытки темы,
теперь проигрывает их по порядку времени. Повтор задачи воркера ничего не задваивает, `progress rebuild`
восстанавливает всё с нуля, как сейчас.

Статусы «слабая / мало данных / в порядке» (PRG-2) остаются для отображения — они про то, **как** человек знает
тему, а срок — про то, **когда** её повторить.

**Шум оценщика.** Балл одной оценки — ±20 (analysis §2.3), поэтому ответ на 65 мог быть оценён на 55 и
сбросить интервал. Насколько это мешает — показывает симуляция (§5.5), а не догадка.

### 5.4. Данные и API

- Миграция `0010` (`0009` уже занята настройками тренировки 010): `topic_progress` + `ease float`,
  `interval_days int`, `reps int`, `due_at timestamptz`.
  После миграции — `progress rebuild` (делаю сам; `due_at null` до пересчёта = «сейчас»).
- `GET /users/{id}/progress`: у темы + `due_at`, `interval_days`. Порядок тем не меняется.
- `POST /sessions` `mode=repeat`: темы — с `due_at ≤ now`, по возрастанию среднего; + поле `force: bool = false`
  (вопрос 1). Нет сроков → `409 nothing_due` с `next_due_at` и темой; нет прогресса вовсе → `409
  nothing_to_repeat`, как сейчас.

### 5.5. Исследование: симуляция под шум оценщика

`research/repetition/simulate.py`, без LLM и БД, секунды на CPU. Модель ученика: у каждой темы «истинное
знание» 0–100; ответ = знание + шум оценщика; повторение поднимает знание, время его снижает (кривая забывания).
Сравниваются правило PRG-2 и SM-2 за 60 «дней» при шуме σ = 0, 10, 20 (10 — разброс при t = 0,7, 20 — допуск
из §2.3): сколько повторений потрачено, сколько тем «забыто» к концу (знание < 60), сколько повторений ушло на
темы, которые и так знает. Допущения модели ученика записываются рядом с результатом: это аргумент «почему
SM-2 и насколько он терпит шум», а не замер на людях. Результат — таблица в `research/README.md` и analysis §2.

Можно выкинуть, если не останется времени, — SM-2 в продукте от неё не зависит.

## 6. Проверка пунктов эталона (приоритет 3)

### 6.1. Что не так сейчас

Ключевые пункты вопроса пишет та же 4B-модель. Если пункт неверен («индекс (a, b) работает для условия
только по b»), оценщик снимает баллы с кандидата, который ответил правильно. Сейчас это видно только в
подробном разборе, и то если модель догадается. Насколько часто пункты неверны — не мерили.

### 6.2. Что видит пользователь

В подробном разборе (бот и веб) у пункта под сомнением — строка «⚠️ Этот пункт эталона, возможно, неверен:
<почему>». Всё остальное — без изменений (вопрос 2).

### 6.3. Как устроено

- Новый промпт `check_key_points/v1`: на вход — вопрос и его пункты, на выход — только сомнительные
  `[{"n": 2, "issue": "…"}]`, обычно пустой список. Отдельный вызов, а не поле в оценке или разборе: урок 2.6 —
  когда модель в одном ответе судит и кандидата, и эталон, она их путает.
- Фоновая задача воркера `check_key_points(session_id)` ставится при создании сессии (тренировка и повторение),
  один вызов модели на сессию — все вопросы сразу. Время сессии для человека не растёт: проверка идёт, пока он
  читает первый вопрос. Оценка первого ответа может подождать её в очереди Ollama (~10–20 с) — замерю.
- Результат — `question.key_points_check jsonb`: `{"issues": [...], "model", "prompt_version", "latency_ms"}`
  (миграция `0011`). `null` — ещё не проверено или сбой; сбой проверки ничего не ломает.
- Разбор (`GET/POST /answers/{id}/review`): у пункта + `doubt: str | null`.
- В логах — только id и число сомнений, без текстов.

### 6.4. Исследование: замер проверки

`research/key_points_check/` — набор, написанный вручную: 10 вопросов из сгенерированных в БД (тексты
вопросов и пунктов — не персональные данные, но набор в `research/data/`, не в git) и к каждому одна подложенная
ошибка в одном пункте (подмена на противоположное, неверное число, перепутанные понятия). Как «лестница» в
спринте 5: синтетика, проверяется одно свойство.

| Метрика | Как считается |
|---|---|
| найдено подложенных | из 10 ошибок отмечено |
| ложные тревоги | отмечено верных пунктов из ~40 |
| сомнительных в «живых» вопросах | доля по всем 47 сгенерированным вопросам БД (без разметки — только частота) |

`--quick` — 5 вопросов. **Правило для продукта:** если ложных тревог больше 1 из 10 вопросов, предупреждение в
разборе не показываем (флаг остаётся в БД для исследования) и записываем это как результат: «самопроверка 4B
не надёжна». Это тоже вывод для диплома.

### 6.5. Результат замера и решение (03.11.2026)

Набор — не выгрузка из БД, а 10 вопросов, написанных вручную (`research/key_points_check/cases.yaml`): у живых
вопросов нет разметки, и среди них самих есть неверные пункты. Пример в промпте сначала совпадал с двумя
вопросами набора — заменён на темы не из набора до полного прогона.

| Метрика | `qwen3.5:4b`, промпт v1 |
|---|---|
| найдено подложенных | 5 из 10 |
| ложные тревоги на верных пунктах | 4 из 40 (в 4 вопросах из 10) + 2 из 30 рядом с ошибкой |
| живые вопросы БД | сомнения в 24 из 42; по ручному просмотру разумны около 5, часть противоречит сама себе |
| время вызова на 5 вопросов | 6–16 с |

Правило §6.4 не выполнено (ложные тревоги в 4 вопросах из 10 при допуске 1), поэтому **проверка выключена по
умолчанию** (`KEY_POINTS_CHECK=false`): без неё фоновый вызов только грел бы Мак. Включённая — ставит задачу при
создании сессии, пишет `question.key_points_check` и показывает «⚠️ Этот пункт эталона, возможно, неверен» в
разборе бота и веба. Вывод для диплома: самопроверка эталона той же 4B-моделью ненадёжна; нужна модель
сильнее (облачная через `LLM_EVAL_*`) или человек.

## 9. Тесты (без Ollama, LLM — фейковый провайдер)

- Подсказка: ключ Redis → `asr_ready` в ответе; бот и веб выбирают текст статуса; воркер ставит
  `downloading` → `ready` / `failed`.
- SM-2: таблица «история баллов → интервал, EF, срок» (сдал/провал/сброс, нижняя граница EF, порядок по времени);
  пересчёт идемпотентен; `rebuild` совпадает с пошаговым; `/repeat` берёт только темы со сроком; `force`;
  `409 nothing_due` с ближайшим сроком; прогресс в боте и вебе показывает срок.
- Проверка пунктов: схема и починка (номер вне диапазона выброшен); задача ставится при создании сессии и
  повторения; сбой модели → `null`, сессия не страдает; `doubt` в разборе; `/forget` удаляет вопросы вместе с
  проверкой.
- `stats`: агрегаты на фикстуре, прогоны датасета не попадают.

## 10. Проверка вживую (сам, быстро, без автора)

`qwen3.5:4b`, по одному прогону, потом `ollama stop`; через API, логи и встроенный браузер:
1. Подсказка: ключ Redis вручную в `downloading` → голосовой фрагмент через API → `asr_ready=false`; вернуть
   `ready`. Модель whisper не удаляю и не перекачиваю.
2. SM-2: `progress rebuild` на текущей БД → сроки разумные; веб «Прогресс» и `/repeat` — во встроенном браузере.
3. Проверка пунктов: `--quick` на наборе §6.4; одна сессия через API — время проверки и задержка первой оценки.
4. `stats` на текущей БД.
5. Логи `api`, `worker`, `bot`, `web` — нет текстов ответов, пунктов и токенов.
