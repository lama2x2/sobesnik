# 002. Слой LLM и генерация, которой можно доверять

Статус: одобрена · 30.09.2026 · спринт 2 ([roadmap](../roadmap.md))

## 1. Цель

Вакансию можно прислать ссылкой. Если ссылка не открывается, пользователь получает просьбу прислать
текст или сохранённую HTML-страницу. Разбор вакансии и генерация вопросов стабильно отдают валидный структурированный результат.
Невалидный ответ модели повторяется, а не превращается сразу в `502`. На «не вакансию» приходит
понятный отказ. Требования и вопросы привязаны к темам из фиксированного справочника. У каждого
вопроса есть 3–6 ключевых пунктов ожидаемого ответа. Вопросы распределены по требованиям и проверяют
понимание, а не опыт. Провайдер (Ollama или OpenAI-совместимый endpoint) и модели для генерации
и оценки переключаются через `.env`. Модель по умолчанию выбрана по замеру на 10 реальных вакансиях.

Вход — проблемы, найденные на живой модели в спринте 1 (001 «Итоги»):

| Проблема | Чем закрывается | Раздел |
|---|---|---|
| На текст «вакансия» модель выдумывает профиль | классификация текста в том же вызове, короткий текст отсекается без LLM | §8.2 |
| Требования в нижнем регистре | правило в промпте и нормализация в коде | §8.3 |
| `is_required = false` не встречается | правило и пример в промпте, метрика в замере | §8.1, §13 |
| Вопросы про опыт, а не на понимание | примеры в промпте, явный запрет, проверка в коде с повтором | §9.3 |
| Разнобой в `stack` (`ci/cd` и т. п.) | словарь синонимов стека, темы из справочника | §7, §8.3 |

## 2. Границы

**Входит:**
- вакансия на входе — текст, ссылка или HTML-страница (§8.0): загрузка страницы с защитой от SSRF,
  извлечение текста (отдельный разборщик для hh.ru и общий для остальных сайтов);
- `generate_structured()` в `packages/llm`: JSON-схема → вызов → валидация Pydantic и доменные
  проверки → до 2 повторов с описанием ошибки;
- провайдер `openai_compatible` (`/chat/completions`, ключ через env);
- роли `gen` и `eval` с раздельными настройками модели и провайдера через env;
- промпты в YAML-файлах с версией «номер + хеш»; параметры генерации лежат вместе с промптом;
- справочник тем (YAML, 60–100 листовых тем), таблица `topic`, синхронизация при старте `api`;
- `topic` у требований и вопросов, `key_points` у вопросов;
- распределение вопросов по требованиям в коде (GEN-1), запрет повторов внутри вакансии (GEN-4);
- отказ на «не вакансию» (VAC-3);
- эндпоинты `GET /vacancies/{id}`, `PATCH /vacancies/{id}` (VAC-4), `GET /sessions/{id}`;
- скрипт замера в `research/` и выбор модели по умолчанию;
- решение из 000 §6: разбор и генерация остаются синхронными или уходят в воркер.

**Не входит:**
- оценка ответа, промпт оценки, рубрика — спринт 3 (роль `eval` только настраивается и видна в `/health/llm`);
- `POST /sessions/{id}/finish` — спринт 3, сводке нужны оценки;
- сессия `repeat` и новый вопрос по слабой теме — спринт 7;
- подмешивание вопросов из банка (GEN-6), `reference_answer`, `dataset_item_id` — спринт 5 и позже;
- авторизация — спринт 6;
- ретраи при недоступности LLM (таймаут, отказ соединения, 5xx). Запрос синхронный, и повтор
  после 120-секундного таймаута только удвоит ожидание. Ретраи на недоступность появятся в воркере
  (спринт 3), где их можно делать с паузой.

## 3. Отклонения от roadmap и 000

1. **Первичный ключ `topic` — `slug`, а не UUID** (000 §7: `id, slug, title, parent_id`). Slug и так уникален
   и неизменен по смыслу. С ним справочник в YAML — единственный источник правды, а в CSV для `research/`
   видно `db.indexes`, а не UUID. Переименование slug обрабатывает `ON UPDATE CASCADE`.
2. **Тема вопроса наследуется от требования.** GEN-2 не говорит, кто выбирает тему вопроса. В сессии по
   вакансии тему выбирает модель при разборе, по одной на требование. Вопрос берёт тему своего требования,
   второй раз модель её не выбирает. У `question` своя колонка `topic_slug`: в сессии `repeat` (спринт 7)
   вопрос будет без требования.
3. **Контракт `GET /health/llm` меняется:** вместо одного провайдера — две роли, `gen` и `eval` (§11).
   Клиентов у API пока нет.
4. **Версия промпта — `v1#<8 hex>`**, то есть номер плюс хеш файла, как у рубрики в 000 §9.
   В спринте 1 было просто `v0`.
5. **Промпты и справочник тем лежат в `packages/core`** как ресурсы пакета. Их чтение через
   `importlib.resources` — единственное I/O в `core`: файлы только читаются и лежат в самом пакете.
   Рубрика в 000 §9 лежит там же.

6. **Вакансия по ссылке и из HTML входит в MVP** (000 VAC-1: только текст; импорт через API hh.ru
   записан в «после MVP»). API hh.ru теперь требует токен приложения: без него `403`, проверено 30.09.2026.
   Поэтому ссылка обрабатывается загрузкой публичной страницы, а не через API. Для прочих сайтов — общий
   извлекатель текста. Импорт через API hh.ru (поиск, подписки) остаётся после MVP.

После одобрения спеки пункты 1, 3 и 6 вписываются в 000 (§4.1 VAC-1, §7, §8).

## 5. Слой LLM (`packages/llm`)

### 5.1. Структурированный вывод с повторами

```python
T = TypeVar("T", bound=BaseModel)

class StructuredResult(BaseModel, Generic[T]):
    value: T
    attempts: list[LLMResponse]   # все ответы, включая невалидные

async def generate_structured(
    llm: LLMProvider,
    request: LLMRequest,
    schema: type[T],
    *,
    json_schema: dict[str, Any] | None = None,   # по умолчанию schema.model_json_schema()
    repair: Callable[[T], T] | None = None,        # детерминированная починка перед check
    check: Callable[[T], list[str]] | None = None, # доменные проверки: список проблем
    max_retries: int = 2,
) -> StructuredResult[T]: ...
```

- Модели передаётся облегчённая схема: структура, типы, `required` и `enum`, но без `minItems`,
  `maxItems`, `minLength`, `maxLength` и `pattern`. Эти ограничения проверяет Pydantic, и нарушение уходит
  на повтор. Причина — скорость грамматики Ollama. Замер на qwen3:8b (M4, 30.09.2026), 5 вопросов с
  `key_points`, одинаковый выход в 716 токенов: полная схема — 96,7 с, облегчённая — 57,8 с, без схемы —
  28,8 с, но ответ невалиден.
- Ответ разбирается так: убирается блок `<think>…</think>` и обёртка ```` ```json ````, если они есть,
  затем `schema.model_validate_json`, затем `repair`, затем `check`.
- Если разбор или проверка не прошли, делается следующая попытка, всего не больше `1 + max_retries`.
  К промпту пользователя добавляется блок «Предыдущий ответ не прошёл проверку: …, верни JSON заново»
  с первыми 5 проблемами. Для ошибок Pydantic в список идут `loc` и `msg`, но не `input`. Если в запросе
  задан `seed`, на попытке `k` он становится `seed + k`.
- Когда попытки кончились, бросается `LLMOutputError(LLMError)` со списком проблем последней попытки
  и числом попыток. API отвечает на него `502 llm_bad_output`.
- `LLMUnavailableError` и прочие `LLMError` не повторяются и пробрасываются сразу.
- В лог попадают число попыток, задержка и токены каждой попытки, `type` и `loc` ошибок. Тексты
  ответов модели и промптов в лог не попадают.

`max_retries = 2` совпадает с EVAL-2, и оценка в спринте 3 будет пользоваться этой же функцией.

**Лимит выхода.** В `LLMRequest` появляется поле `max_tokens`: для Ollama это `options.num_predict`,
для OpenAI-совместимого API — `max_tokens`. Разбор ограничен 2 048 токенами, генерация — 300 токенами
на вопрос плюс 300. Без лимита зациклившаяся модель генерирует до конца контекста: на замере
`qwen3:1.7b` так упёрлась в 600-секундный таймаут. С лимитом обрезанный ответ не проходит валидацию
и уходит на повтор, а худший случай ограничен тремя попытками.

### 5.2. Провайдер `openai_compatible`

- `POST {base_url}/chat/completions`, заголовок `Authorization: Bearer {api_key}`, если ключ задан.
  Тело: `model`, `messages` (system + user), `temperature`, `seed`, `stream: false`.
- Structured output задаётся через `LLM_STRUCTURED`:
  - `json_schema` (по умолчанию): `response_format = {"type": "json_schema", "json_schema": {"name": "answer",
    "schema": …, "strict": false}}`. `strict: false`, потому что strict-режим OpenAI требует, чтобы все поля
    были `required`, а схемы Pydantic с значениями по умолчанию этому не соответствуют;
  - `json_object`: `response_format = {"type": "json_object"}`, а схема дописывается в конец системного промпта.
    Нужен для endpoint'ов, которые не понимают `json_schema`.
- Токены берутся из `usage.prompt_tokens` и `usage.completion_tokens`, модель — из поля `model` ответа.
- Ошибки: таймаут, отказ соединения, `429` и `5xx` — это `LLMUnavailableError`. `401` и `403` — это
  `LLMError("неверный ключ API")`: такую ошибку не исправить ожиданием. `404` — `LLMUnavailableError`
  («модель не найдена»). Прочие `4xx` — `LLMError`.
- `health()`: `GET {base_url}/models`. Ответ `200` и модель есть в списке — `ok`. Пустой список или endpoint
  без `/models` (`404`) — тоже `ok` с пометкой «список моделей недоступен». `401` и `403` — «неверный ключ».
- Ollama сама отдаёт OpenAI-совместимый API на `/v1`. Поэтому провайдер проверяется живым тестом без
  облачного ключа: `LLM_PROVIDER=openai_compatible`, `LLM_BASE_URL=http://host.docker.internal:11434/v1`.

### 5.3. Настройки провайдера и роли

```python
class LLMConfig(BaseModel):
    provider: Literal["ollama", "openai_compatible", "fake"]
    base_url: str
    model: str
    api_key: str | None = None      # SecretStr, в логах и /health не показывается
    timeout_s: float = 120.0
    num_ctx: int | None = None      # только ollama
    structured: Literal["json_schema", "json_object"] = "json_schema"  # только openai_compatible

def make_provider(config: LLMConfig) -> LLMProvider: ...
```

У приложения две роли:
- `gen` — разбор вакансии и генерация вопросов;
- `eval` — оценка ответов, используется со спринта 3.

Базовые настройки роли — `LLM_*`. Роль может переопределить четыре из них: `LLM_GEN_PROVIDER`,
`LLM_GEN_BASE_URL`, `LLM_GEN_API_KEY`, `LLM_GEN_MODEL`, для оценки то же с префиксом `LLM_EVAL_`.
Незаданное значение берётся из базового. Если итоговые конфигурации ролей совпадают, создаётся один
провайдер на обе роли.

`create_app(settings, llm=...)` по-прежнему принимает один провайдер для тестов, и он становится
провайдером обеих ролей. Отдельно можно передать `llm_eval=`.

## 6. Промпты в файлах

Один промпт — один YAML-файл: `packages/core/src/sobesnik_core/prompts/<name>/v<N>.yaml`.

```yaml
temperature: 0.0
seed: 42            # или null
system: |
  Ты — опытный технический интервьюер…
user: |
  Справочник тем:
  $topics

  Текст вакансии:
  $vacancy_text
```

- Подстановка через `string.Template.substitute`: `$имя`. Фигурные скобки в примерах JSON экранировать
  не нужно. Если переменная не передана, это `KeyError`.
- `load_prompt(name, version=None) -> PromptTemplate`. Без `version` берётся файл с наибольшим `N`.
  `PromptTemplate.version = "v1#" + sha256(содержимое файла)[:8]`. Это значение сохраняется в
  `vacancy.prompt_version` и `question.prompt_version`. Правка файла без смены номера меняет хеш,
  и её видно в данных.
- Параметры генерации (`temperature`, `seed`) лежат в том же файле, поэтому версия промпта фиксирует
  и их. Для разбора — `temperature 0`, `seed 42`: одинаковая вакансия даёт одинаковый профиль.
  Для вопросов — `temperature 0.7` без `seed`: в новой сессии нужны новые вопросы.
- Выбор версии через env в этом спринте не делается. Он понадобится для сравнения промптов оценки
  в спринте 5.

## 7. Справочник тем

`packages/core/src/sobesnik_core/topics.yaml` — две ступени: область и листовая тема.

```yaml
- slug: db
  title: Базы данных
  topics:
    - {slug: db.sql, title: SQL-запросы, JOIN, агрегация}
    - {slug: db.indexes, title: Индексы и планы запросов}
    - {slug: db.transactions, title: Транзакции и уровни изоляции}
    - {slug: db.general, title: Базы данных — общее}
```

- Slug: `^[a-z0-9_]+(\.[a-z0-9_]+)?$`, у листа префикс — slug области. Модель выбирает только листовые темы.
- В каждой области есть лист `<область>.general`: требование, которое не легло ни в одну тему,
  попадает туда, а не в случайную тему.
- Состав — 12–14 областей, 60–100 листов. Предварительно:

  | Область | Примеры листов | Листов |
  |---|---|---|
  | `python` | модель данных, коллекции и сложность, генераторы, asyncio, GIL и потоки, типизация, память и GC | 8–9 |
  | `jvm` | коллекции, многопоточность, память и GC, Spring | 5–6 |
  | `go` | горутины и каналы, интерфейсы, память, контекст | 4–5 |
  | `frontend` | event loop, TypeScript, React, рендеринг в браузере, CSS | 6–7 |
  | `lang` | C#/.NET, C++, PHP, Kotlin, Swift, Rust — по одной теме на язык | 6–8 |
  | `db` | SQL, индексы, транзакции, нормализация, оптимизация запросов, NoSQL, репликация и шардирование, ORM | 8–9 |
  | `web` | HTTP, проектирование REST, gRPC, аутентификация (OAuth, JWT), WebSocket | 5–6 |
  | `arch` | SOLID и паттерны, микросервисы, очереди сообщений, кэширование, согласованность в распределённых системах, system design | 7–8 |
  | `devops` | Linux, Docker, Kubernetes, CI/CD, наблюдаемость, облака, IaC | 7–8 |
  | `testing` | пирамида тестов, моки, интеграционные тесты, нагрузка | 4–5 |
  | `security` | OWASP, криптография в приложениях, секреты | 3–4 |
  | `cs` | алгоритмы и сложность, структуры данных, ОС и процессы, сети (TCP/IP, DNS) | 4–5 |
  | `data` | ETL и хранилища, Spark, ML-основы, MLOps | 4–5 |

- Там же — словарь синонимов для `stack`: `postgres → postgresql`, `k8s → kubernetes`, `js → javascript`,
  `ci/cd → ci-cd` и т. п., около 30 пар.
- Таблица `topic` синхронизируется с YAML при старте `api`: новые темы добавляются, заголовки и родители
  обновляются. Темы, которых нет в YAML, не удаляются: на них могут ссылаться требования и прогресс.
  Модели предлагаются только темы из YAML.

## 8. Разбор вакансии (VAC)

### 8.0. Откуда берётся текст: текст, ссылка, HTML

`POST /vacancies` принимает ровно одно из полей: `text`, `url` или `html`. Дальше во всех трёх случаях
получается текст вакансии, и он идёт в разбор (§8.1) с теми же проверками, включая VAC-3.

**Ссылка:**
1. Проверка ссылки: только `http` и `https`, длина до 2 000 символов. Хост резолвится, и если хотя бы один
   адрес приватный, loopback, link-local или multicast, ссылка отклоняется (`422 url_not_allowed`).
   Та же проверка повторяется на каждом редиректе. Без неё сервер можно заставить ходить во внутреннюю сеть
   (SSRF). Для локальных экспериментов проверку можно отключить: `FETCH_ALLOW_PRIVATE=true`.
2. Загрузка через httpx: таймаут 10 с, не больше 5 редиректов, не больше 3 МБ (читается потоком
   и обрывается на лимите), `content-type` должен быть `text/html`. User-Agent — честный,
   `Mozilla/5.0 (compatible; Sobesnik/0.1; +https://github.com/lama2x2/sobesnik)`. На 30.09.2026 hh.ru
   отдаёт такому клиенту страницу вакансии с кодом `200`.
3. Извлечение текста (§8.0.1).
4. Любой сбой шагов 2–3 даёт `422 url_unreadable` с сообщением «Не получилось прочитать вакансию
   по ссылке. Пришлите текст вакансии или сохранённую страницу (.html)». Сбоем считаются сеть, таймаут,
   ответ не `200`, не HTML, превышение размера, капча или пустая страница, извлечённый текст короче
   `MIN_VACANCY_CHARS`. Причина пишется в лог, но не в ответ пользователю.

**HTML** — содержимое сохранённой страницы, до 3 МБ. Бот в спринте 6 скачает присланный `.html`-файл
и передаст его содержимое этим полем. Для извлечения берётся хост из `<link rel="canonical">` или
`og:url`, если они есть, иначе используется общий извлекатель. Если извлечь не удалось, приходит
`422 html_unreadable` с просьбой прислать текст.

#### 8.0.1. Извлечение текста

- **hh.ru** (любой поддомен, путь `/vacancy/<id>`): заголовок из `data-qa="vacancy-title"`, описание из
  `data-qa="vacancy-description"`, ключевые навыки из `data-qa="skills-element"`, опыт из
  `data-qa="vacancy-experience"`. Всё собирается в текст «Должность / Опыт / Описание / Ключевые навыки».
  Если разметка изменится и блоки не найдутся, срабатывает общий извлекатель.
- **Общий:** `trafilatura` (основной текст страницы без меню и подвала). Её лицензия (Apache-2.0)
  проверяется при добавлении зависимости. Если лицензия не подойдёт — `lxml` и эвристика: самый
  длинный блок текста.
- Извлечённый текст длиннее `MAX_VACANCY_CHARS` обрезается по границе абзаца. Модель всё равно
  разбирает начало вакансии, а короткий текст отклоняется как `url_unreadable`.
- В БД сохраняется извлечённый текст (`raw_text`), источник и ссылка. HTML не сохраняется.

### 8.1. Схема ответа модели

```python
TextKind = Literal["vacancy", "resume", "other"]

class ParsedRequirement(BaseModel):
    text: str               # 1–500
    is_required: bool
    topic: str              # обязательная строка; что это slug листа, проверяет check

class ParsedVacancy(BaseModel):
    kind: TextKind          # первое поле: модель сначала решает, что за текст
    profile: VacancyProfile | None   # null, если kind != "vacancy"
```

`VacancyProfile` — как в 001 §6, только `requirements` теперь `list[ParsedRequirement]`. JSON-схема
собирается кодом, и `topic` в ней — обязательная строка.

Сначала `topic` был `enum` из 97 слагов, чтобы грамматика Ollama не пропустила выдуманную тему. На живой
модели это вдвое замедлило разбор: 34,5 с против 18,5 с при том же выходе в 285 токенов (qwen3:8b, M4,
30.09.2026). Поэтому `enum` из схемы убран. Модель берёт slug из списка в промпте, а тема вне
справочника ловится проверкой и уходит на повтор.

Без `enum` модели придумывают правдоподобные слаги: `lang.kotlin`, `web.frameworks`, `arch.asyncio`.
При повторе с описанием ошибки они повторяют ту же ошибку, поэтому на замере `qwen3.5:4b` провалила 1 разбор
из 10. Поэтому неизвестная тема сначала чинится в коде (`repair`), без повтора:
- тема из справочника остаётся как есть;
- если область слага есть в справочнике (`lang.kotlin` → область `lang`), тема становится `<область>.general`;
- иначе тема не меняется, и её ловит проверка.

Число починенных тем пишется в лог и в замер.

Доменные проверки (`check`, с повтором): при `kind = "vacancy"` профиль не `null`; `topic` есть в справочнике
(после починки остаются только слаги с неизвестной областью, и повтор перечисляет допустимые области);
текст требований не повторяется.

Промпт `parse_vacancy/v1` включает список листовых тем (slug и заголовок) и два коротких примера:
вакансию с блоком «будет плюсом» (там `is_required = false`) и резюме (там `kind = resume`).
Отдельно сказано: требования пишутся обычным предложением с заглавной буквы, нижний регистр —
только для `stack`.

### 8.2. Отказ на «не вакансию» (VAC-3)

- Текст короче `MIN_VACANCY_CHARS = 80` символов после обрезки пробелов сразу получает
  `422 not_a_vacancy`, без вызова LLM. Слово «вакансия» или «python junior» не разбираются.
- `kind = "resume"` → `422 not_a_vacancy` с сообщением «Похоже на резюме. Пришлите текст вакансии:
  требования работодателя к кандидату».
- `kind = "other"` → `422 not_a_vacancy` с сообщением «Не похоже на вакансию…».
- Отказ ничего не пишет в БД.

Классификация делается в том же вызове, что и разбор, а не отдельным запросом. Иначе разбор длился бы
дольше на время ещё одного прохода по тексту вакансии.

### 8.3. Нормализация в коде

После валидации, до записи в БД:
- `stack`: обрезка, нижний регистр, замена по словарю синонимов, удаление дублей с сохранением порядка;
- требования: если текст начинается со строчной кириллической буквы, первая буква делается заглавной.
  Латиницу не трогаем, чтобы не испортить `iOS` или `gRPC`.

### 8.4. Что хранится (VAC-5)

Как в спринте 1: `raw_text`, `parser_model`, `prompt_version` (теперь `v1#…`). Добавляются `source`
(`text | url | html`) и `source_url`. У требования добавляется `topic_slug`.

## 9. Генерация вопросов (GEN)

### 9.1. План: какие требования проверяет каждый вопрос (GEN-1)

План строит код, а не модель. Функция `plan_questions(requirements, n, asked_counts)` в `packages/core`:

1. Требования сортируются по ключу: сколько вопросов по нему уже было задано в прошлых сессиях этой
   вакансии (меньше — раньше), затем обязательные раньше желательных, затем порядок в вакансии.
2. Первый проход: требования берутся по порядку, но если тема требования уже есть в плане, оно
   откладывается. Так пять вопросов не уйдут в одну тему, если в вакансии есть другие.
3. Второй проход добирает отложенные требования. Если `n` больше числа требований, список проходится
   по кругу, и одно требование получает несколько слотов.

Результат — список из `n` слотов `{requirement_index, aspect}`, где `aspect` — номер вопроса по этому требованию
(1, 2, …). Функция чистая и детерминированная, покрывается юнит-тестами.

### 9.2. Схема ответа и промпт

```python
class GeneratedQuestion(BaseModel):
    text: str                          # 1–1000
    key_points: list[str]              # 3–6 пунктов, каждый 1–300 символов

class GeneratedQuestions(BaseModel):
    questions: list[GeneratedQuestion] # ровно n: minItems = maxItems = n
```

`requirement_index` из схемы уходит: вопрос `i` отвечает слоту `i` плана, и требование ему назначает код.
Тема вопроса — тема требования (§3 п. 2).

Промпт `generate_questions/v1` получает должность, уровень, стек и пронумерованный план:
«1. [обязательно] Индексы в PostgreSQL (тема: db.indexes)». Если требование встречается в плане второй раз,
промпт просит вопрос о другом его аспекте. В промпте есть:
- что значит уровень для сложности: junior — «что это и как работает», middle — «почему и какие
  компромиссы», senior и lead — границы применимости, отказы, проектирование;
- жанры хороших вопросов с примерами: объяснить механизм, сравнить два подхода, что будет, если…,
  найти проблему в описанной ситуации, выбрать решение и обосновать;
- явный запрет: не спрашивать о личном опыте, проектах и предпочтениях кандидата («расскажите,
  как вы…», «приходилось ли вам…»), на такой ответ нельзя поставить балл по рубрике;
- `key_points` — проверяемые утверждения, которые должны прозвучать в хорошем ответе, а не темы
  («B-tree поддерживает диапазонные запросы», а не «про B-tree»);
- вопросы на русском, термины можно на английском; на вопрос можно ответить устно за 1–3 минуты,
  без написания кода.

### 9.3. Доменные проверки с повтором

`check` для вопросов возвращает проблему, если:
- вопрос похож на вопрос об опыте. Это регулярные выражения по нормализованному тексту: «расскажи(те)
  о (своём|вашем) опыте», «приходилось ли», «(был|есть) ли у (тебя|вас)», «в (твоём|вашем) (проекте|опыте)»,
  «с какими … (ты|вы) работал(и)», «как (ты|вы) (обычно|использовал)». Вопросы-сценарии («как бы вы
  решили…») проходят;
- два вопроса сессии совпадают после нормализации (нижний регистр, без пунктуации и лишних пробелов);
- вопрос совпадает с уже заданным по этой вакансии.

Список шаблонов «вопроса об опыте» лежит в `packages/core/checks.py` и покрыт тестами на положительные
и отрицательные примеры.

### 9.4. Без повторов (GEN-4)

В пределах сессии повторы отсекает проверка из §9.3. Для новой сессии по той же вакансии:
- план ставит вперёд требования, по которым спрашивали меньше всего (§9.1);
- в промпт передаются последние 30 вопросов, уже заданных по этой вакансии, с просьбой их не повторять.

GEN-4 для сессии `repeat` («новый вопрос по слабой теме») — спринт 7.

### 9.5. Что хранится (GEN-5)

`question`: `gen_model`, `prompt_version` (`v1#…`), `topic_slug`, `key_points`, `requirement_id`.

## 11. API

Новое и изменённое по сравнению с 001 §8. Формат ошибок тот же.

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `GET /health/llm` | — | `200`/`503` `{"status", "roles": {"gen": {ok, provider, model, detail}, "eval": {…}}}`; `503`, если не в порядке хотя бы одна роль |
| `POST /vacancies` | `{user_id, text \| url \| html}` — ровно одно | `201` профиль; `422 not_a_vacancy`, `url_not_allowed`, `url_unreadable`, `html_unreadable` |
| `GET /vacancies/{id}` | — | `200` профиль; `404 vacancy_not_found` |
| `PATCH /vacancies/{id}` | `{level?, remove_requirements?: [uuid]}` | `200` профиль |
| `POST /sessions` | `{vacancy_id, n?}` | `201` сессия |
| `GET /sessions/{id}` | — | `200` сессия; `404 session_not_found` |

Если в запросе нет ни одного из полей или их больше одного, ответ — стандартный `422`.

Профиль вакансии: добавляются `source` и `source_url`, у требования — `topic` (slug или `null`).

```json
{"id": "…", "text": "Индексы и планы запросов в PostgreSQL", "is_required": true, "topic": "db.indexes"}
```

Вопрос в сессии: добавляются `topic` и `key_points`.

```json
{
  "id": "…", "position": 1, "requirement_id": "…", "topic": "db.indexes",
  "text": "Почему составной индекс (a, b) не помогает запросу с условием только по b?",
  "key_points": ["B-tree упорядочен по первому столбцу", "…"]
}
```

`key_points` отдаются клиенту, чтобы их было видно в демо и при проверке качества. Бот не должен
показывать их до ответа: это правило войдёт в спеку бота (спринт 6).

`PATCH /vacancies/{id}` (VAC-4):
- `level` — новый уровень. Следующие сессии генерируются под него;
- `remove_requirements` — id удаляемых требований. У вопросов по ним `requirement_id` становится `null`,
  тема вопроса сохраняется;
- `422 requirement_not_found`, если id не из этой вакансии; `422 no_requirements_left`, если удаляются все;
- пустое тело — `422`.

Ошибки LLM — как в 001: `502 llm_bad_output` (теперь после 3 попыток), `502 llm_error`, `503 llm_unavailable`.

## 13. Выбор модели по умолчанию

**Данные.** Это не юнит-тесты: юнит-тесты работают на FakeProvider и синтетических текстах. Здесь
живые модели сравниваются на реальных данных.
- 10 реальных вакансий с hh.ru: разные стеки (Python, Java, Go, фронтенд, DevOps, QA, данные, мобильная
  разработка) и уровни от junior до lead. Ищу их сам и загружаю через извлекатель из §8.0, так что он
  заодно проверяется на живых страницах. В репозиторий идут ссылки и разметка
  (`research/generation_bench/labels.yaml`: ссылка, ожидаемый `kind`, уровень, есть ли блок «будет плюсом»).
  Тексты кэшируются в `research/data/vacancies/` и в репозиторий не попадают: это чужие тексты, а вакансию
  могут снять с публикации.
- 8 текстов «не вакансия» пишу сам: вымышленное резюме, пост соискателя, описание компании без требований,
  статья, рецепт, одно слово, сообщение из чата, список технологий без контекста. Они вымышленные,
  поэтому лежат в репозитории рядом с разметкой.

**Модели.** Mac с 16 ГБ RAM, на SSD свободно около 13 ГБ. Поэтому кандидатов три, и скачивается только одна
новая модель:
- `qwen3:8b` — уже скачана, текущая модель;
- `qwen3:1.7b` — уже скачана, ориентир для режима без GPU;
- `qwen3.5:4b` (3,4 ГБ) — новая модель. Сначала планировалась модель другого семейства, но из подходящих
  по размеру (до ~5,5 ГБ) на 30.09.2026 это `gemma4:e2b` (4,6 ГБ, класс 2B) и `lfm2.5:8b` (MoE с ~1B
  активных параметров). Новое поколение Qwen размером 4B — более вероятный кандидат в модель по умолчанию
  для Мака с 16 ГБ: она занимает ~3,5 ГБ RAM против 7,5 ГБ у `qwen3:8b` с контекстом 16k. Во время
  проверки спринта `qwen3:8b` вместе с виртуальной машиной Docker (8 ГБ) заняли swap на 8,3 из 9,2 ГБ.
  Сравнение семейств между собой — задача спринта 5. Если модель проиграет, её удаляю после замера (`ollama rm`).

Модели 12B и больше не рассматриваются: на 16 ГБ RAM они вместе с Docker работают на пределе, и места на диске на них нет.

**Скрипт.** `docker compose run --rm tools uv run python research/generation_bench/run.py --models …`.
Он вызывает те же функции сервисов, что и API, но без БД, и пишет CSV в `research/data/` и сводную
таблицу в Markdown.

**Метрики:**

| Метрика | Как считается |
|---|---|
| валидно с первой попытки / после повторов | доля вызовов разбора и генерации |
| время разбора, время генерации 5 вопросов | медиана и максимум, токены |
| VAC-3 | вакансии приняты и «не вакансии» отклонены, из 18 |
| уровень | совпадение с разметкой, из 10 |
| `is_required = false` | есть хотя бы в одной вакансии с блоком «будет плюсом» |
| вопросы про опыт | доля по проверке из §9.3 до повторов и ручная проверка 50 вопросов лучшей модели |
| `key_points` | доля вопросов, где пункты — утверждения, а не темы (ручная проверка выборки) |

**Решение.** Модель по умолчанию — лучшая по VAC-3, уровню и вопросам, если её медианное время укладывается
в ориентиры 000 §5 (разбор ≤ 30 с, 5 вопросов ≤ 40 с). Если медиана и p95 с учётом повторов меньше 60 с,
разбор и генерация остаются синхронными в запросе (закрывает решение из 000 §6). Иначе — перенос в воркер
в спринте 3. Таблица и решение записываются в «Итоги».

## 14. Тесты

Без Ollama и сети, FakeProvider и `httpx.MockTransport`.

- `packages/llm`:
  - `generate_structured`: валидно с первой попытки; невалидный JSON → повтор → успех; провал `check` → повтор
    с описанием проблем в промпте; три провала → `LLMOutputError` с числом попыток; `LLMUnavailableError`
    не повторяется; `seed` сдвигается; `<think>` и ```` ```json ```` вырезаются; в лог не попадает текст ответа;
  - `OpenAICompatibleProvider`: тело запроса и `Authorization`, оба режима `LLM_STRUCTURED`, разбор `usage`,
    отображение `401`/`403`/`404`/`429`/`5xx`/таймаута, `health()` во всех ветках;
  - `make_provider(LLMConfig)` для всех трёх провайдеров.
- `packages/core`:
  - `load_prompt`: последняя версия по умолчанию, хеш меняется при правке, отсутствующая переменная → `KeyError`;
    все промпты из пакета загружаются и рендерятся;
  - справочник: slug уникальны и по шаблону, у листов есть область, в каждой области есть `.general`,
    листов 60–100; в JSON-схеме разбора `topic` обязателен и без `enum`;
  - нормализация `stack` и регистра требований;
  - `plan_questions`: обязательные раньше желательных; разнообразие тем; `n` больше числа требований;
    приоритет ни разу не спрошенных требований; детерминированность;
  - проверки вопросов: шаблоны «про опыт» на 10+ положительных и 10+ отрицательных примерах, дубли.
- `apps/api`, источники вакансии (`httpx.MockTransport` и подменённый резолвер DNS):
  - отклоняются схемы, отличные от `http(s)`, приватные, loopback и link-local адреса, в том числе после
    редиректа на такой адрес; `FETCH_ALLOW_PRIVATE` снимает проверку;
  - таймаут, `404`, `403`, не-HTML, ответ больше 3 МБ и больше 5 редиректов дают `url_unreadable`;
  - извлекатель hh.ru на синтетическом HTML с разметкой `data-qa` (не копия реальной страницы) и переход
    на общий извлекатель, если блоков нет; общий извлекатель на простой статье;
  - обрезка по `MAX_VACANCY_CHARS`; `html` с `canonical` на hh.ru идёт в разборщик hh.ru;
  - `POST /vacancies` с `url` и с `html`: в БД сохраняются `source`, `source_url` и извлечённый текст;
    без полей или с двумя полями — `422`.
- `apps/api`:
  - разбор: happy path с темами; `not_a_vacancy` для короткого текста (провайдер не вызывается), `resume`
    и `other`; невалидный ответ → повтор → `201`; три невалидных → `502 llm_bad_output`;
  - сессия: вопрос `i` привязан к требованию слота `i` и к его теме; `key_points` сохраняются; вопрос
    про опыт → повтор; во второй сессии по вакансии промпт содержит прошлые вопросы, а план начинается
    с неспрошенных требований;
  - `GET`/`PATCH /vacancies/{id}`, `GET /sessions/{id}` со всеми ошибками из §11;
  - роли: `LLM_EVAL_MODEL` без прочих переопределений даёт второй провайдер с той же базой; одинаковые
    конфигурации дают один провайдер; `/health/llm` в состояниях «всё ок», «gen недоступна», «eval недоступна»;
  - синхронизация тем идемпотентна; миграции `upgrade → downgrade → upgrade` и `compare_metadata`.
- Живые тесты (`-m ollama`): разбор реальной вакансии с темами; отказ на резюме; генерация 5 вопросов
  с `key_points`; тот же разбор через `openai_compatible` на `…:11434/v1`.
- Живой тест загрузки (`-m network`, по умолчанию пропускается): одна вакансия hh.ru по ссылке из
  `labels.yaml` превращается в текст длиннее `MIN_VACANCY_CHARS`. Если hh.ru поменяет разметку,
  это будет видно здесь.

## 16. Критерии приёмки

1. 10 вакансий из замера загружаются по ссылке hh.ru, разбираются, и по каждой генерируется сессия из 5 вопросов на модели
   по умолчанию. `502 llm_bad_output` не встречается ни разу.
2. Все 8 текстов «не вакансия» получают `422 not_a_vacancy`, все 10 вакансий принимаются.
   Недоступная ссылка и ссылка на страницу, где нет вакансии, дают `422 url_unreadable` с просьбой
   прислать текст или HTML. Та же вакансия, сохранённая из браузера как `.html`, разбирается через поле `html`.
3. У каждого требования есть тема из справочника. У каждого вопроса есть тема, требование и 3–6 `key_points`.
4. Среди вопросов модели по умолчанию нет вопросов про личный опыт: проверка §9.3 и ручной просмотр 50 вопросов.
5. Смена `LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL` в `.env` переключает разбор и генерацию на OpenAI-совместимый
   endpoint без правки кода. Облачного ключа нет, поэтому проверка идёт на `/v1` Ollama. `/health/llm`
   показывает обе роли.
6. VAC-1…5 и GEN-1…5 закрыты тестами по таблице трассировки; тесты проходят при выключенной Ollama.
7. `pytest`, `ruff check`, `ruff format --check`, `mypy` зелёные в `tools`.
8. Таблица замера, модель по умолчанию и решение «синхронно или воркер» записаны в «Итоги».
   `LLM_MODEL` в `.env.example` и `Settings` обновлён.

## 17. Решения по открытым вопросам

1. **Облачного ключа нет.** Переключение провайдера проверяется на `/v1` самой Ollama: код провайдера
   тот же, что и для облака.
2. **Модели: 16 ГБ RAM, мало места на SSD.** Кандидаты — две уже скачанные модели и одна новая (§13).
3. **`key_points` отдаются в API всегда.** До ответа пользователя их скрывает бот (спринт 6).
4. **Вакансии для замера** собираю сам с hh.ru по ссылкам (§13).
