# 010. Буфер: подробный разбор, настройки тренировки, чистка сомнений

Статус: одобрена 03.11.2026 (все вопросы — А, §13). Спринт 10 (roadmap §10).

## 1. Цель

Закрыть то, что переносилось из спринтов 5–7, и только то, что заметно пользователю и не ломает уже
работающий MVP. Одним предложением: **под оценкой появляется кнопка «📖 Разобрать подробно» — эталонный ответ,
разбор по пунктам и что почитать; перед тренировкой можно выбрать «только обязательное» и сложность; в
сомнениях распознавания остаются только похожие на огрехи распознавания пункты, а вопросы реже строятся на
неверной посылке.** Всё — и в боте, и в вебе.

## 4. Подробный разбор ответа (EVAL-9, приоритет 1)

### 4.1. Что видит пользователь

Под оценкой — кнопка **«📖 Разобрать подробно»** (бот: рядом с «Почему такие баллы?»; веб: под советом).
По нажатию: «📖 Готовлю разбор… обычно 20–40 секунд» (бот — с «печатает…», веб — `data-wait`, как у генерации),
потом:

```
📖 Разбор

Как мог бы ответить сильный кандидат:
<эталон, 4–8 предложений>

По пунктам:
✅ B-tree упорядочен по первому столбцу — сказано верно.
❌ Индекс (a, b) не помогает условию только по b — не прозвучало: <почему так, 1–2 предложения>
⚠️ Покрывающий индекс избавляет от чтения таблицы — сказано наоборот: <как правильно>

Неточности в ответе:
• «индекс всегда ускоряет запись» → наоборот, каждый индекс замедляет INSERT и UPDATE.

⚠️ В самом вопросе неточность: <если есть, §7>

📚 Почитать: <ссылки темы из карты>
```

Повторное нажатие отдаёт сохранённый разбор сразу, без модели.

### 4.2. Как устроено

- **Статусы пунктов ставит код, а не модель:** из последней оценки — `wrong_points` → ⚠️, `missed_points` → ❌,
  остальные → ✅. Модель только пишет комментарий к каждому пункту. Так разбор не спорит с оценкой.
  У вопроса без ключевых пунктов блока «По пунктам» нет.
- **Неточности** — до 3 пар «цитата из ответа → как правильно». Цитата проверяется кодом: если её нет в тексте
  ответа (после нормализации регистра и пробелов), пункт выбрасывается — модель не приписывает человеку слов.
- **Ссылки не генерирует модель.** Берутся из `topic_docs.yaml` по теме вопроса (1–3 ссылки, как сейчас под
  проваленной оценкой), но в разборе показываются всегда, и при зачтённом ответе (вопрос 2).
- **Флаг вопроса** `question_issue` — строка или пусто: если сам вопрос содержит неверное утверждение (§7).
- Промпт `review_answer/v1` (YAML рядом с остальными): вопрос, ключевые пункты с номерами, эталон вопроса, если
  есть, ответ (или расшифровка, с тем же правилом «устную речь и кириллицу не штрафовать»), упущенные и неверные
  пункты из оценки, совет. Temperature 0, seed как у оценки. JSON по схеме, `generate_structured` с ретраями.
- **Синхронно в API**, как генерация вопросов (таймаут LLM тот же): разбор нужен по кнопке и не чаще раза на
  ответ; отдельная задача воркера и событие в Redis здесь — лишний код. Если Ollama занята оценкой следующего
  ответа, разбор подождёт её в очереди Ollama.

### 4.3. Данные

Новая таблица `answer_review` (миграция):

| Поле | Значение |
|---|---|
| id | uuid |
| answer_id | FK → answer, `ON DELETE CASCADE` |
| evaluation_id | FK → evaluation, **unique**: один разбор на оценку; переоценка — новый разбор |
| provider, model, prompt_version | как у оценки (EVAL-3) |
| content | jsonb: `reference`, `points[{n, comment}]`, `mistakes[{quote, correction}]`, `question_issue` |
| raw_response, latency_ms, tokens_in, tokens_out, created_at | как у оценки |

Ссылки и тексты пунктов в `content` не хранятся — их подставляет код при выдаче (карта ссылок может обновиться).
Два одновременных нажатия: вставка `ON CONFLICT (evaluation_id) DO NOTHING`, отдаётся то, что в БД.

**Персональные данные.** Разбор цитирует ответ, поэтому:
- `/forget scope=all` — удаляется вместе с ответом (каскад);
- `/forget scope=audio` — разборы голосовых ответов удаляются вместе с расшифровками (в ответе `DELETE /users/{id}/data` —
  новое поле `reviews_deleted`);
- в логах — только id, модель, задержка, число неточностей; текстов нет.

### 4.4. API

| Метод и путь | Назначение |
|---|---|
| `POST /answers/{id}/review` | разбор последней оценки ответа: есть — `200` из БД; нет — вызов модели и `200` |

Ответ:

```json
{
  "answer_id": "…", "evaluation_id": "…", "cached": false,
  "reference": "…",
  "points": [{"n": 1, "text": "B-tree упорядочен…", "status": "ok|missed|wrong", "comment": "…"}],
  "mistakes": [{"quote": "…", "correction": "…"}],
  "question_issue": null,
  "docs": [{"title": "…", "url": "…"}],
  "model": "qwen3.5:4b", "latency_ms": 23100
}
```

Ошибки: чужой или несуществующий ответ — `404 answer_not_found`; ответ ещё не оценён или оценка `failed` —
`409 answer_not_evaluated`; ответ датасета — `404`; модель не ответила по схеме после ретраев —
`502 llm_bad_output` / `503 llm_unavailable` (как у генерации), бот и веб пишут «Не получилось разобрать, попробуйте ещё раз».
Авторизация — как у `GET /answers/{id}`: сервисный токен бота или токен пользователя веба.

### 4.5. Бот и веб

- Бот: кнопка `ReviewCb(answer_id)` под оценкой; разбор — отдельным сообщением (HTML, обрезка до 4 096 с
  сохранением ссылок); кнопка под оценкой после разбора не исчезает (второе нажатие — из БД, мгновенно).
- Веб: кнопка `hx-post="/answers/{id}/review"` → фрагмент `_review.html` под оценкой; на странице прошлого
  вопроса, если разбор уже есть, — сразу показан свёрнутым (`<details>`).

## 5. Настройки тренировки (GEN-7, приоритет 2)

### 5.1. Что видит пользователь

- **Только обязательные** — вопросы только по требованиям с признаком «обязательно».
- **Сложность** — «проще» / «как в вакансии» (по умолчанию) / «сложнее».

Бот: под профилем вакансии кнопка **«⚙️ Настройки»** → экран с переключателями «☑ Только обязательные» и
«Сложность: проще · ✓ как в вакансии · сложнее» и «← Назад». Настройки запоминаются для пользователя (в
состоянии бота, как выбор тем) и действуют на все тренировки: «Начать», 5/10/15, выбор тем, `/repeat`.
Под профилем, если настройки не по умолчанию, — строка «⚙️ только обязательные · сложнее» (вопрос 3).

Веб: в форме тренировки на странице вакансии — флажок «Только обязательные требования» и выпадающий список
«Сложность»; на странице прогресса у «Повторить» — тот же список сложности.

### 5.2. Как устроено

- **Сложность — сдвиг уровня на шаг**, промпт не меняется: «проще» для `middle` → в промпт идёт `junior`,
  «сложнее» → `senior`; на краях (`intern`, `lead`) уровень не сдвигается дальше. В вакансии уровень не меняется.
- **Только обязательные** — фильтр требований до плана (`plan_questions`), вместе с `topics`: берётся пересечение.
- Повторение (`mode=repeat`): `difficulty` работает, `required_only` не задаётся (там темы, а не требования).

### 5.3. API и данные

`POST /sessions` — два необязательных поля, старые клиенты работают как раньше:

```json
{"vacancy_id": "…", "n": 5, "topics": ["db.indexes"], "required_only": true, "difficulty": "harder"}
```

- `difficulty`: `easier | same | harder`, по умолчанию `same`; `required_only`: по умолчанию `false`.
- `422 no_required_requirements` — в вакансии (или в выбранных темах) нет обязательных требований; текст для
  человека: «В вакансии нет обязательных требований — снимите „только обязательные“».
- `422` на `required_only` в `mode=repeat` (как сейчас на `topics`).
- В `session` — колонки `required_only bool not null default false`, `difficulty text not null default 'same'`
  (миграция); отдаются в `GET /sessions/{id}`. Уровень, с которым генерировались вопросы, виден по сессии.

## 6. Фильтр шумных сомнений распознавания (приоритет 3)

### 6.1. Что не так сейчас

На 10 фрагментах 005 — 28 пунктов `asr_doubts`, полезна примерно треть (research/README). Полезные: «рак» → RAG,
«Селлари» → Celery, «инио» → `__init__`. Шум — стилистические перефразы: «закрыт доступ» → «скрыт от глаз»,
и добавки слов: «хранить» → «пароли хранить».

### 6.2. Правило

Чистая функция `filter_doubts(doubts) -> list[str]` в `packages/core` (без LLM):

1. Пункт разбирается как «распознано «X» — возможно, сказано «Y» [или «Z»]». Не разобрался — **остаётся**
   (лучше лишний пункт, чем потерянный).
2. X и каждый вариант Y переводятся в латиницу (транслитерация + грубая фонетика: `c/k`, `w/v`, `дж/j/g`…),
   общие слова X и Y убираются, остатки сравниваются по сходству строк (0…1). Берётся лучший вариант Y.
3. Остаток X или Y пуст (добавили или выкинули слово) — **убрать**.
4. X кириллицей, Y латиницей и сходство ≥ 0,8, или остатки совпали полностью — это просто написание
   («джейсон» = JSON, «skiplocked» = SKIP LOCKED) — **убрать**.
5. Сходство < 0,55 — перефраз, не похоже по звучанию — **убрать** (вопрос 4).

Прототип на 51 сохранённом в БД пункте: остаётся ~20 — почти все похожи на огрехи распознавания; уходят
перефразы. Теряется 2–3 полезных на границе (например, «update4» → FOR UPDATE держится ровно на пороге).

### 6.3. Где применяется

При выдаче, а не при записи: `GET /answers/{id}` отдаёт отфильтрованный список, бот и веб показывают его.
В `evaluation.feedback.asr_doubts` и в CSV для исследования остаётся всё, что вернула модель — правило можно
менять без перепрогонов, и старые оценки тоже чистятся. В лог — только сколько пунктов убрано.

## 7. Вопросы с неверной посылкой (приоритет 4)

Пример из 007: вопрос повторения утверждал «status — первый столбец в индексе (id, status)», хотя первый — `id`.
Отвечать на такой вопрос бессмысленно, а оценка штрафует за «несогласие» с вопросом.

Две дешёвые меры, без второго вызова модели на каждую генерацию (+15 с к каждой тренировке — дорого):

1. **Промпт `generate_questions/v2`**: правило «не утверждай в вопросе фактов, в которых не уверен; если вопрос
   строится на условии („есть индекс (id, status)…“), условие задаётся явно и выводы из него в вопрос не
   вписываются — их должен сделать кандидат» и плохой пример рядом с хорошим. Версия промпта сохраняется у
   вопроса (GEN-5), старые вопросы не трогаются.
2. **Флаг в разборе** (§4.2, `question_issue`): если вопрос всё же неверен, разбор говорит об этом прямо —
   «⚠️ В самом вопросе неточность: в индексе (id, status) первый столбец — id».

Отдельной метрики не делаем: быстрая проверка — 2–3 генерации повторения по `db.indexes` до и после правки
(§9), глазами.

## 8. Тесты (без Ollama, LLM — фейковый провайдер)

- Разбор: схема и починка (номера пунктов вне диапазона, цитата не из ответа выброшена, `question_issue`
  пустой → `null`); статусы пунктов из оценки; повторный вызов не зовёт модель; гонка двух вызовов → одна
  строка; `404` чужой / датасета, `409` не оценён; `/forget audio` и `all` удаляют разборы; ссылки из карты.
- Бот: кнопка под оценкой, разбор отдельным сообщением, обрезка длинного разбора, ошибки `502`/`503`.
- Веб: кнопка и фрагмент, сохранённый разбор на прошлом вопросе.
- Настройки: сдвиг уровня и края; `required_only` + `topics`; `422` без обязательных; `repeat` + `difficulty`;
  бот — экран настроек, запоминание, применение к «Начать», 5/10/15, темам и `/repeat`; веб — форма.
- Фильтр сомнений: таблица примеров (кириллица, добавка слова, перефраз, полезные огрехи, неразобранный формат).
- Промпт генерации v2 рендерится; `prompt_version` у новых вопросов — v2.

## 9. Проверка вживую (сам, быстро, без автора)

Через API и встроенный браузер, `qwen3.5:4b`, по одному прогону, потом `ollama stop`:
1. Ответ «не знаю» и средний ответ → разбор: время, есть эталон, пункты совпадают с оценкой, неточности —
   цитаты из ответа, ссылки темы. Второе нажатие — мгновенно.
2. Голосовой фрагмент из `research/data/asr_check` → сомнения до/после фильтра (только число, без текстов в логах).
3. Сессия «только обязательные» + «сложнее» → все вопросы по обязательным требованиям, в промпте уровень выше.
4. 2–3 генерации повторения по `db.indexes` на v2 — нет ли утверждений-посылок.
5. Веб: кнопка разбора и настройки в форме; бот — через логи и тесты (руками — в чеклисте).

## 11. Критерии приёмки

1. По кнопке в боте и вебе приходит разбор: эталон, пункты со статусами как в оценке, ссылки только из карты.
   Повторное нажатие не вызывает модель.
2. `/forget` удаляет разборы (`all` — все, `audio` — голосовых ответов); в логах нет текстов разборов.
3. Сессия с `required_only` содержит вопросы только по обязательным требованиям; `difficulty` сдвигает уровень
   в промпте; без новых полей всё работает как раньше (регрессия бота и веба).
4. Сомнения распознавания в боте и вебе проходят фильтр; в CSV — исходные.
5. Новые вопросы генерируются промптом v2.
6. `pytest`, `ruff check`, `ruff format --check`, `mypy` зелёные; юнит-тесты без Ollama и сети.
7. В «Итогах» — один общий чеклист автора: новое этого спринта + непройденные пункты 009.
