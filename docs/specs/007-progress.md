# 007. Прогресс и повторение слабых тем

Статус: одобрена · 02.11.2026 ([roadmap](../roadmap.md))

## 1. Цель

Система помнит, как человек отвечал по каждой теме, честно показывает, где он слаб, и возвращает к слабым
темам новыми вопросами (С4–С6, PRG-1…4). Рядом со слабой темой — 1–3 проверенные ссылки «что почитать».
Перед тренировкой можно выбрать темы вакансии кнопками.

Вход из прошлых спринтов (roadmap §7, 006 §16, research/README.md):

| Что | Чем закрывается | Раздел |
|---|---|---|
| PRG-1 прогресс темы после каждой оценки | `topic_progress`, пересчёт в воркере | §4 |
| PRG-2 слабая тема, пороги в конфиге | статус темы с учётом шума ±20 | §5 |
| PRG-3 сессия повторения | `POST /sessions {mode: "repeat"}` без нового промпта | §6.2 |
| PRG-4 история сессий | в ответе `GET /users/{id}/progress` | §7.1 |
| выбор тем (006 §16) | `topics` в `POST /sessions`, кнопки в боте | §6.1, §8.3 |
| «что почитать» (006 §16) | `topic_docs.yaml`, проверка ссылок тестом `network` | §9 |
| `/forget` всех данных (С6) | `DELETE /users/{id}/data?scope=all` | §7.3 |
| балл шумит на ±20 (research, вывод 3) | «мало данных» до N попыток, среднее, «≈ число» | §5 |

## 2. Границы

**Входит:**
- таблица `topic_progress` и её пересчёт после каждой боевой оценки; команда `sobesnik-cli progress rebuild`
  для уже накопленных ответов;
- статус темы: «слабая» / «мало данных» / «в порядке», пороги в env;
- `POST /sessions`: `topics` для сессии по вакансии и режим `repeat`;
- `GET /users/{id}/progress`; `DELETE /users/{id}/data?scope=all`; ссылки темы в `GET /answers/{id}`;
- бот: `/progress`, `/repeat`, `/forget` с выбором «только голос / всё», кнопка «🎯 Выбрать темы» у вакансии,
  1–2 ссылки под слабой оценкой;
- карта «тема → что почитать» на все листовые темы справочника (97 тем), юнит-тест формата и тест `network`
  на доступность ссылок.

**Не входит:**
- подробный разбор ответа по кнопке (эталон, ошибки, выбор ссылок моделью) — спринт 10, возьмёт ссылки отсюда;
- тренировка только по обязательным требованиям, выбор сложности, генерация пачками — спринт 10 (006 §16);
- интервальное повторение (через сколько дней вернуться к теме), графики прогресса, прогресс в вебе (спринт 9);
- прогресс по исследовательским данным: ответы датасетов и оценки прогонов в прогресс не попадают.

## 3. Отклонения от 000

1. **`is_weak` не хранится.** В `topic_progress` лежат только факты (попытки, последние баллы), а статус темы
   считается при чтении по текущим порогам. Иначе смена порогов в env требовала бы пересчёта всех строк.
2. **PRG-2 смягчено правилом «мало данных»** (§5): одна оценка не делает тему слабой, и правило «последний
   балл меньше 50» не действует само по себе — один шумный балл не должен перекрашивать тему. Это открытый
   вопрос 1–2 (§13).
3. **Повторение не требует вакансии.** `session.vacancy_id = null`, `mode = repeat`; вопросы привязаны
   к теме и к требованию, на котором тема провалилась (§6.2).

## 4. Прогресс темы (PRG-1)

**Что считается попыткой.** Ответ пользователя (`answer.source = user`) с боевой оценкой (`done`, без прогона,
003 §7) на вопрос с темой. Пропущенные вопросы, неудачные оценки (`failed`) и переоценки прогонами не
считаются. Один ответ — одна попытка, сессии по вакансии и повторения учитываются одинаково.

**Таблица `topic_progress`** (PK `user_id, topic_slug`): `attempts`, `last_score`, `last_scores int[]`
(до трёх последних, новые первыми), `avg_last3 float`, `updated_at`.

**Пересчёт.** В воркере, в той же транзакции, что и статус ответа `done`: строка темы считается заново из БД
(три последние боевые оценки по `answer.created_at` и общее число попыток), а не «прибавлением». Так повтор
задачи arq и повторная оценка ничего не сломают: пересчёт идемпотентен. Логика расчёта — чистая функция
в `packages/core/progress.py`, БД — в `apps/api/services/progress.py`.

**Старые данные.** `sobesnik-cli progress rebuild [--user ID]` пересчитывает все строки — один раз после
миграции для ответов спринта 6.

## 5. Как не врать про «слабость» темы (PRG-2)

Балл одной оценки шумит на ±20 (research: модель против самой себя на перефразах и между моделями). Среднее
трёх попыток шумит заметно меньше (≈ ±12), одна попытка — ничего не доказывает. Поэтому у темы три статуса:

| Статус | Условие (по умолчанию) | Как показываем |
|---|---|---|
| ⚪ мало данных | попыток меньше `PROGRESS_MIN_ATTEMPTS = 2` | «≈ 40 · 1 попытка — пока мало данных» |
| 🔴 слабая | попыток ≥ 2 и среднее последних трёх < `PROGRESS_WEAK_AVG = 60` | «≈ 45 · 3 попытки» + ссылки |
| 🟢 в порядке | попыток ≥ 2 и среднее ≥ 60 | «≈ 80 · 4 попытки» |

- Числа — «≈», округлённые до 5, как в оценке (006 §8.2). Точных средних пользователь не видит.
- Внутри «мало данных» темы с баллом < 60 выделены: «похоже, стоит повторить» — честно и без приговора.
- `/repeat` берёт сначала слабые темы, потом «мало данных» с баллом < 60 (вопрос 3, §13): иначе после
  первой проваленной тренировки повторять было бы нечего, а демо из roadmap («провалить → /repeat → ответить
  хорошо → тема не слабая») не проходилось бы.
- Пример. Тема `db.indexes`: 40 → «мало данных, похоже стоит повторить» → `/repeat` → 85 → среднее 62,5 →
  «в порядке». Если было 40 и 35 (слабая) и потом 85 — среднее 53 → всё ещё слабая; нужна ещё одна хорошая
  попытка. Это честно: одна удачная попытка после двух провалов — тоже шум.
- В `/progress` под списком одна строка мелко: «Баллы примерные: одна оценка ошибается на ±20, поэтому
  смотрим среднее последних трёх попыток».
- Пороги — env `PROGRESS_MIN_ATTEMPTS`, `PROGRESS_WEAK_AVG`, `PROGRESS_LOW_SCORE` (60, порог «похоже стоит
  повторить»). API отдаёт их в ответе прогресса, чтобы бот не держал свои копии.

## 6. Сессии

### 6.1. Выбор тем: `topics` в `POST /sessions`

```json
{"vacancy_id": "…", "n": 5, "topics": ["db.indexes", "python.asyncio"]}
```

- `topics` необязателен; если задан — план строится только по требованиям вакансии с этими темами
  (тот же `plan_questions`, отфильтрованный список). Тема не из вакансии → `422 topics_not_in_vacancy`.
- Одна выбранная тема и 5 вопросов — 5 вопросов по её требованиям с разными аспектами (план уже это умеет).
- В `session.topics text[] null` сохраняется выбор — для истории.

### 6.2. Повторение: `POST /sessions {mode: "repeat"}` (PRG-3)

```json
{"mode": "repeat", "user_id": "…", "n": 5}
```

- Темы: слабые от самых низких, потом «мало данных» с низким баллом (§5); не больше `n`, по одному вопросу
  на тему. `n` по умолчанию 5, предел 3…15, как у обычной сессии. Тем нет → `409 nothing_to_repeat`.
- **Без нового промпта.** Для каждой темы берётся требование последнего вопроса пользователя по ней
  (текст требования, тема, обязательность). Из них собирается профиль: заголовок «Повторение слабых тем»,
  уровень и стек — последней вакансии среди этих требований. Дальше — тот же `generate_questions`.
- `asked` — все прежние вопросы пользователя по этим темам: вопросы новые, но по тем же темам (С5).
  Защита от повторов уже есть (`question_problems`).
- Вопрос ссылается на исходное требование (`requirement_id`) и тему; `session.vacancy_id = null`,
  `mode = repeat`. Ответы и оценки идут обычным путём, прогресс пересчитывается (С5).
- Требование удалено (`SET NULL`) или его нет — в профиль идёт строка «Тема: <заголовок темы>».
- План ставит обязательные требования раньше; в сессии вопросы переставляются обратно — от самой слабой темы.

## 7. API

### 7.1. `GET /users/{id}/progress` (С4, PRG-4)

```json
{
  "thresholds": {"min_attempts": 2, "weak_avg": 60, "low_score": 60},
  "topics": [
    {"slug": "db.indexes", "title": "Индексы и планы запросов", "status": "weak",
     "attempts": 3, "last_score": 45, "avg_last3": 48.3,
     "docs": [{"title": "PostgreSQL: индексы", "url": "https://postgrespro.ru/docs/postgresql/17/indexes"}]}
  ],
  "sessions": [
    {"id": "…", "created_at": "…", "mode": "vacancy", "vacancy_title": "Python-разработчик",
     "answered": 5, "passed": 3, "avg_total": 62.0, "scores": [70, 45, null, 80, 55]}
  ]
}
```

- `status`: `weak` | `few` | `ok`, `low` — «мало данных» с баллом ниже `low_score`; темы отсортированы: слабые по возрастанию среднего, потом «мало данных»,
  потом «в порядке». `docs` — у всех тем (бот сам решает, где показывать).
- `sessions` — последние 5 (параметр `sessions_limit`, до 20), новые первыми; `scores` по позициям,
  `null` — пропуск или нет оценки.

### 7.2. Ссылки в `GET /answers/{id}`

У ответа появляются `topic` и `docs` (до 2 первых ссылок темы). Бот показывает их под непройденной оценкой.

### 7.3. `DELETE /users/{id}/data?scope=all` (С6)

Удаляет всё о пользователе: аудио в S3 (как `scope=audio`), транскрипты, ответы и их оценки (в том числе
оценки прогонов — каскадом), сессии, их вопросы, вакансии с требованиями, `topic_progress`. Запись `users`
остаётся (только id и `telegram_id`), `settings` сбрасываются. Ответ:
`{"audio_deleted", "transcripts_deleted", "answers_deleted", "vacancies_deleted", "sessions_deleted"}`.
Сначала удаляются объекты S3, потом строки одной транзакцией; сбой S3 — `503 storage_unavailable`, строки не трогаются (как в 004 §8.5).

### 7.4. Ошибки

| Код | Когда |
|---|---|
| `422 topics_not_in_vacancy` | в `topics` тема, которой нет в требованиях вакансии |
| `409 nothing_to_repeat` | `repeat`, а слабых и «похоже стоит повторить» тем нет |
| `404 user_not_found` | прогресс, повторение или удаление для неизвестного `user_id` |

## 8. Бот

### 8.1. `/progress`

> 📊 **Прогресс**
>
> 🔴 **Слабые темы**
> • Индексы и планы запросов — ≈ 45 · 3 попытки
>   📚 [PostgreSQL: индексы](…) · [Use The Index, Luke](…)
>
> ⚪ **Мало данных**
> • asyncio и асинхронный код — ≈ 40 · 1 попытка, похоже стоит повторить
> • HTTP — ≈ 75 · 1 попытка
>
> 🟢 **В порядке:** SQL ≈ 80 (4) · Docker ≈ 75 (2)
>
> **Последние тренировки**
> 02.11 · Python-разработчик · 3 из 5 пройдено · ≈ 60
> 01.11 · Повторение · 2 из 2 · ≈ 80
>
> _Баллы примерные: одна оценка ошибается на ±20, поэтому смотрим среднее последних трёх попыток._
>
> [🔁 Повторить слабые темы]

- Ссылки — только у слабых тем, не больше двух, одной строкой. «В порядке» — одной строкой через «·»,
  заголовок темы до двоеточия. Больше 10 тем в группе — первые 10 и «и ещё N».
- Пусто — «Пока нечего показать: ответьте на пару вопросов — и здесь появятся темы».

### 8.2. `/repeat`

`/repeat [N]` или кнопка → статус «🧩 Готовлю вопросы по слабым темам…» → обычная тренировка (006 §4.3),
вопрос подписан «Повторение · Тема: …». `409 nothing_to_repeat` → «Слабых тем нет 🎉 Пройдите тренировку
по вакансии — /train». Сводка в конце — как обычно, кнопки «Новая вакансия» и «Прогресс».

### 8.3. Выбор тем

Под профилем вакансии добавляется кнопка «🎯 Выбрать темы» → сообщение со списком тем требований вакансии,
по кнопке на тему (✅/⬜, слабые помечены 🔴), снизу [▶️ Начать (5 вопросов)] [Отмена]. Нажатие темы
перерисовывает клавиатуру. Выбор хранится в состоянии бота (Redis), в `callback_data` — номер темы
в списке (UUID и slug не влезают в 64 байта). Ничего не выбрано — кнопка «Начать» неактивна (ответ
«Выберите хотя бы одну тему»).

### 8.4. Ссылки под оценкой

Под непройденной оценкой (🔴 «Слабо») одна строка: «📚 Почитать: [asyncio — документация Python](…)».
Не больше двух ссылок, превью ссылок отключено (`link_preview_options.is_disabled`), чтобы не раздувать
сообщение.

### 8.5. `/forget`

«Что удалить?» [🎙 Только голос] [🗑 Всё] [Отмена]. «Только голос» — как сейчас (006). «Всё» → второе
подтверждение: «Удалить вакансии, ответы, оценки и прогресс? Отменить нельзя.» [Да, удалить всё] [Отмена] →
`scope=all` → «Удалено: 3 вакансии, 24 ответа, 5 голосовых. Начнём заново — пришлите вакансию.» Состояние
бота пользователя сбрасывается.

### 8.6. Прочее

`/help` и `/start` упоминают `/progress` и `/repeat`; список команд в меню Telegram (`set_my_commands`)
дополняется.

## 9. «Что почитать»: карта ссылок

**Файл** `packages/core/src/sobesnik_core/topic_docs.yaml` — отдельно от `topics.yaml`, чтобы справочник
тем оставался читаемым:

```yaml
python.asyncio:
  - {title: "asyncio — документация Python", url: "https://docs.python.org/3/library/asyncio.html"}
  - {title: "Асинхронность в Python — Real Python", url: "https://realpython.com/async-io-python/"}
```

**Правила сбора** (собирает Claude вручную при реализации, модель приложения в этом не участвует):
- сначала официальная документация (docs.python.org, postgresql.org / postgrespro.ru, kubernetes.io,
  developer.mozilla.org, go.dev, …), потом известные открытые руководства (learn.javascript.ru, OWASP,
  Use The Index, Luke, …); без платных курсов, пейволов и статей-однодневок;
- 1–3 ссылки на тему; русская — если есть хорошая (postgrespro.ru, learn.javascript.ru, kubernetes.io/ru, MDN ru);
- каждая ссылка открыта и прочитана при сборе: страница открывается и говорит именно про эту тему;
  `*.general` — обзорные страницы области (учебник, руководство);
- храним только адрес и короткое название (≤ 60 символов), текст страниц не копируем.

**Код.** `load_topic_docs()` в `sobesnik_core.topics` рядом с `load_topics()`; API отдаёт ссылки из ресурса
пакета, в БД они не хранятся (это контент, а не данные пользователя).

**Тесты.**
- Юнит (без сети): у каждой листовой темы 1–3 ссылки, все `https://`, slug есть в справочнике, нет
  дублей адресов внутри темы, название ≤ 60 символов.
- `pytest -m network` (`test_topic_docs_alive`): каждая ссылка GET-запросом (свой User-Agent, редиректы,
  таймаут 15 с, по 8 параллельно) отвечает < 400, и после редиректов остаётся на том же сайте и не на его
  главной странице (признак «страницу убрали»). Тест собирает все битые ссылки и падает одним сообщением
  со списком — видно сразу всё. Сайты, которые режут ботов (403 на любой запрос), отмечаются в YAML
  `check: false` с комментарием и в тесте пропускаются с предупреждением.

## 10. Миграция `0006_progress`

- таблица `topic_progress` (§4), FK на `users` и `topic` (`ON DELETE CASCADE` по пользователю);
- `session.mode`: в `CHECK` добавляется `repeat`; `session.topics text[] null`;
- данные не трогает: прогресс по старым ответам — `sobesnik-cli progress rebuild`.

## 11. Тесты

- `core/progress`: расчёт из списка баллов, границы порогов (1 попытка; 2 попытки на 59,5 и 60; новые первыми),
  выбор тем для повторения и их порядок.
- Пересчёт в воркере: после оценки строка появилась и обновилась; повтор задачи не задваивает попытку;
  `failed`-оценка, пропуск, оценка прогона и ответ датасета не считаются; `rebuild` даёт то же, что пересчёт.
- `POST /sessions`: `topics` фильтрует план, чужая тема — `422`; `repeat` выбирает темы в нужном порядке,
  передаёт прежние вопросы в `asked`, `409` без тем; генерация — фейковым провайдером.
- `GET /users/{id}/progress`: статусы, сортировка, ссылки, история с пропусками.
- `DELETE …?scope=all`: удаляется всё перечисленное в §7.3 (S3 — фейковым хранилищем), чужие данные целы,
  сбой S3 — строки на месте.
- Бот (мок API): тексты `/progress` для пустого, «мало данных» и смешанного случаев; `/repeat` и `409`;
  выбор тем — переключение, «Начать» с выбранными, пустой выбор; ссылки под слабой оценкой и их нет под
  хорошей; `/forget` с двумя шагами.
- Карта ссылок: юнит-тест формата и `network`-тест доступности (§9).

## 12. Быстрая живая проверка

Демо из roadmap, одна сессия, `qwen3.5:4b`, без замеров:
1. вакансия → «🎯 Выбрать темы» → одна тема → 3 вопроса, на один ответить «не знаю»;
2. `/progress` — тема «мало данных, похоже стоит повторить», ссылки у слабых; под проваленной оценкой — ссылка;
3. `/repeat` → один вопрос по этой теме → ответить хорошо → `/progress` — тема «в порядке»;
4. `/forget` → «Всё» → `/progress` пуст;
5. `pytest -m network` — список битых ссылок пуст; `ollama stop qwen3.5:4b`.

## 13. Открытые вопросы

1. **Когда тема может стать «слабой».** Человек один раз ответил на вопрос по индексам на 40.
