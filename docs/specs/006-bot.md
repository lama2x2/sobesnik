# 006. Telegram-бот

Статус: одобрена · 02.11.2026 · спринт 6 закрыт ([roadmap](../roadmap.md))

## 1. Цель

Весь сценарий тренировки проходится в Telegram текстом и голосом (С1–С3): вакансия → профиль с правкой уровня →
вопросы по одному → ответ текстом или голосом → статус «распознаю → оцениваю» → оценка → следующий вопрос →
сводка. Бот — **тонкий клиент** API: он ничего не решает о вакансиях, вопросах и оценках, только переводит
сообщения Telegram в вызовы API и ответы API — в сообщения. Результат обработки ответа бот получает событием
из Redis, а не опросом.

Вход из прошлых спринтов (roadmap §6, 000 §6, 003 «Итоги», 004 «Итоги», research/README.md):

| Что | Чем закрывается | Раздел |
|---|---|---|
| события смены статуса ответа в Redis (ANS-3) | Redis Streams, публикует воркер | §6 |
| сервисный токен бота (BOT-3) | `API_SERVICE_TOKEN`, проверка в API | §5.1 |
| `/admin/eval-runs`, `/admin/evaluations.csv`, `/admin/datasets` и админ-токен | эндпоинты поверх тех же сервисов, что у CLI | §5.2 |
| генерация вопросов (~40 с) синхронно или в воркере | остаётся синхронной, правило пересмотра | §9 |
| балл шумит на ±20 (research, вывод 3) | балл показывается словом и «≈ число», без ложной точности | §8.2 |
| сомнения в распознавании полезны на треть (research) | показываются свёрнутыми и как вопрос, а не как факт | §8.3 |

Живые проверки — только быстрые (§12): одна вакансия, 3 вопроса, один текстовый и один голосовой ответ,
после — `ollama stop`.

## 2. Границы

**Входит:**
- `apps/bot` на Aiogram 3, сервис `bot` в compose (тот же образ, другая команда);
- команды `/start`, `/new`, `/train`, `/forget` (голос), `/help`; правка уровня кнопками; ответ текстом и голосом;
  кнопка «Пропустить вопрос»; сводка в конце сессии;
- статусное сообщение и индикатор «печатает…» (BOT-6), сообщения об ошибках и о недоступности LLM;
- allowlist по `telegram_id` (BOT-5);
- события статуса ответа: воркер пишет в Redis Stream, бот читает группой потребителей (§6);
- сервисный токен для `/api/v1/*` и админ-токен для `/api/v1/admin/*` (§5);
- служебные эндпоинты `/admin/datasets`, `/admin/eval-runs`, `/admin/evaluations.csv` (§5.2);
- том у Redis, чтобы состояние бота и непрочитанные события переживали перезапуск (§7.3).

**Не входит:**
- `/progress`, `/repeat` и `/forget` всех данных — спринт 7 (roadmap); `/forget` для голоса входит (§15 п. 4);
- удаление лишних требований кнопками (VAC-4 в API есть, в боте — только уровень, как в roadmap);
- вакансия по сохранённой HTML-странице файлом — принимается, если это несложно (§4.2), иначе текст и ссылка;
- импорт голосового датасета через HTTP: аудиофайлы датасета лежат на диске, остаётся только CLI (§5.2);
- подробный разбор ответа с источниками и прочая гибкость тренировки — в планах, §16;
- генерация вопросов в воркере (§9), вебхуки Telegram (только long polling: инстанс за NAT, без домена),
  несколько языков интерфейса, пользовательская авторизация (с веб-кабинетом).

## 3. Отклонения от roadmap и 000

1. **События — Redis Streams, а не Pub/Sub** (000 §6 оставлял выбор). Pub/Sub теряет событие, если бот в этот
   момент перезапускается, а голосовой ответ обрабатывается до минуты. Stream с группой потребителей хранит
   непрочитанное, и бот дочитывает его после старта. Стоит это одной команды `XADD` в воркере и
   `XREADGROUP`/`XACK` в боте.
2. **Сервисный токен — общий для всех `/api/v1/*`, кроме `/health*`,** и включается, только если задан
   `API_SERVICE_TOKEN`. Пусто — проверки нет (как сейчас), API пишет предупреждение при старте. Иначе
   сломались бы `research/*/check.py` и привычный `curl`; в них добавляется заголовок из env.
3. **Владение не проверяется:** API доверяет сервисному клиенту, бот передаёт только «свои» id из своего
   состояния. Проверка «сессия принадлежит пользователю» появится с пользовательской авторизацией (000 §8).
4. **`/api/v1/admin/*`, а не `/admin/*`:** префикс у всех путей API один (000 §8 опускает его в таблице).
5. **Redis получает том** (сейчас без тома, 003 §8.3). Очереди arq это не мешает: повторная постановка
   безопасна, а воркер и так подхватывает зависшее из БД.

## 4. Сценарии в боте

Тексты ниже — образец, точные формулировки правятся по ходу. Все долгие вызовы API идут под индикатором
«печатает…» (§7.2).

### 4.1. `/start` и `/help` (С1, BOT-2)

`/start` → `PUT /users/telegram/{id}` (найти или создать) → короткая инструкция:

> Привет! Я тренирую к техническим собеседованиям.
> 1. Пришлите текст вакансии или ссылку на неё — я разберу стек и уровень.
> 2. Нажмите «Начать тренировку» — задам 5 вопросов.
> 3. Отвечайте текстом или голосовым. Оценка — через 15–60 секунд.
>
> Оценку ставит небольшая локальная модель: балл примерный (±20), смотрите на упущенные пункты и совет.
> Голосовые проходят через серверы Telegram, на этом инстансе хранятся 30 дней.

`/help` — то же плюс список команд. `user_id` из API кэшируется в состоянии бота (§7.3).

### 4.2. Вакансия (С1, VAC-1…4)

- Любой текст вне ожидания ответа на вопрос считается вакансией. `/new` — явно «жду новую вакансию»
  (сбрасывает текущую сессию в состоянии бота, сессия в API остаётся незавершённой).
- Текст из одной ссылки `http(s)://…` → `POST /vacancies {url}`, иначе `{text}`. Документ `.html` (≤ 3 МБ) →
  `{html}`. Слишком длинный текст и прочие `422` — сообщение из ответа API.
- Сразу статус «📄 Разбираю вакансию… обычно 30–50 с», под индикатором. Ответ API → статус редактируется в профиль:

> **Python-разработчик (Middle)**
> Стек: Python, FastAPI, PostgreSQL, Redis, Docker
> Требования:
> • ✱ Асинхронный Python (asyncio)
> • ✱ PostgreSQL, индексы, транзакции
> • Docker, CI/CD
> (✱ — обязательные)
>
> [Intern] [Junior] [**· Middle ·**] [Senior] [Lead]
> [▶️ Начать тренировку]

- Кнопка уровня → `PATCH /vacancies/{id} {level}` → сообщение перерисовывается с новой отметкой.
- Ошибки разбора: `422 not_a_vacancy`, ссылка не читается и т. п. — текст из `error.message` API
  (он уже человеческий, 002), `503 llm_unavailable` — «Модель сейчас недоступна, попробуйте через минуту»
  (§8.4).

### 4.3. Тренировка (С2)

- «Начать тренировку» или `/train [N]` (N = 3…15, по умолчанию 5) → `POST /sessions {vacancy_id, n}` под
  статусом «🧩 Готовлю 5 вопросов… обычно около 40 с». Нет вакансии в состоянии — «Сначала пришлите вакансию».
  Если в состоянии есть незавершённая сессия этой вакансии, `/train` продолжает её с первого вопроса без ответа
  (`GET /sessions/{id}`), а кнопка «Новая сессия» создаёт новую.
- Под профилем вакансии, кроме «Начать тренировку» (5 вопросов или продолжение), — кнопки «10 вопросов» и
  «15 вопросов»: длинная тренировка без знания команды `/train N`. Генерация 15 вопросов синхронная, около
  1,5–2 мин на Mac — укладывается в таймаут клиента 150 с; статус «Готовлю 15 вопросов…» держится всё это время.
- Вопрос: «Вопрос 2 из 5 · Тема: python.asyncio» + текст + кнопка [Пропустить]. Ключевые пункты не показываются.
- Ответ — любое текстовое сообщение (не команда), пока бот ждёт ответа на вопрос.
  → `POST /sessions/{id}/questions/{qid}/answer` → `202` → статусное сообщение (§4.5).
- Следующий вопрос — по ответу на вопрос 3 (§14): после оценки (вариант А) или сразу после приёма (Б).
- «Пропустить» — к следующему вопросу без ответа. После последнего вопроса и всех оценок →
  `POST /sessions/{id}/finish` → сводка (§8.5).

### 4.4. Голосовой ответ (С3)

- Голосовое (`voice`), кружочек (`video_note`) или аудиофайл (`audio`) в режиме ответа. Бот скачивает файл из Telegram **в память**
  (без диска), отправляет `POST …/answer/voice` (multipart `file`) и забывает байты. Ни содержимое, ни имя файла
  не логируются.
- Telegram сам ограничивает скачивание ботом 20 МБ — меньше лимита API (25 МБ). Длительность и формат
  проверяет API: `422 audio_too_long`, `audio_too_short`, `audio_unsupported`, `413` — понятный текст и
  «ответьте ещё раз или текстом». `503 storage_unavailable` — «не получилось сохранить запись, ответьте текстом».
- После распознавания (событие `evaluating`) статус дополняется расшифровкой (§8.3), чтобы пользователь
  видел, что распознано, ещё до оценки (С3).
- `failed` с `asr_empty` — «Не расслышал речь. Запишите ещё раз или ответьте текстом»; `audio_unreadable` —
  «Не получилось прочитать запись…»; `asr_failed` — «Распознавание не сработало…». Ответить на тот же вопрос
  можно снова: API разрешает новый ответ после `failed` (003 §8.1).

- **Кружочек.** Это mp4 с видео (H.264) и звуком (AAC). Бот отправляет его как есть, API видит дорожку
  видео и до сохранения перекладывает звук в m4a без перекодирования (PyAV, `strip_video`), так что в хранилище
  попадает только голос, лица нет. Дальше — как голосовое. Не удалось отделить звук — `422 audio_unsupported`.

### 4.5. Статусное сообщение (BOT-6)

Одно сообщение на ответ, бот редактирует его по событиям (§6):

| Событие | Голос | Текст |
|---|---|---|
| `202` от API | «✅ Принято. 🎧 Распознаю речь…» | «✅ Принято. 🧠 Оцениваю ответ…» |
| `transcribing` | без изменений | — |
| `evaluating` | «🧠 Оцениваю ответ…» + расшифровка | без изменений |
| нет финального события 60 с | + «Модель думает дольше обычного, ответ сохранён» | то же |
| `done` | статус → оценка (§8) | то же |
| `failed` | статус → сообщение об ошибке (§8.4), индикатор снимается | то же |

Индикатор «печатает…» идёт от приёма ответа до финального события, но не дольше 15 мин (таймаут задачи).

### 4.6. Пограничные случаи ввода

Найдены на первой живой проверке (§12) и разбором кода после неё.

| Случай | Что делает бот |
|---|---|
| Текст длиннее 4 096 символов Telegram режет на несколько сообщений | Склеивает части: сообщение от 3 500 символов считается возможным началом, бот ждёт продолжение до 2 с; часть короче 3 500 — последняя, склейка уходит сразу. Короткие сообщения обрабатываются без задержки. Так же для ответа на вопрос |
| Пока идёт разбор вакансии или генерация вопросов, приходит новая вакансия, `/train` или повторное нажатие кнопки | «⏳ Ещё работаю над предыдущим запросом» — второй долгий вызов к модели не запускается |
| Ссылка без схемы (`hh.ru/vacancy/1`), ссылка с парой слов вокруг, слово-гиперссылка | Ссылка берётся из сущностей Telegram (`url`, `text_link`), схема дописывается. Ссылка одна и текста вокруг меньше 80 символов (минимум вакансии) — вакансия по ссылке, иначе текстом |
| Вакансия пересылкой из канала: фото с подписью | Подпись — как текст |
| Аудио файлом (документ `audio/*`) в режиме ответа | Как голосовое |
| Кружочек (`video_note`) в режиме ответа | Как голосовое; API хранит только звук (§4.4) |
| Обычное видео, стикер, фото без подписи | «Пришлите текст, ссылку или голосовое» |
| Вакансия длиннее 20 000, ответ длиннее 5 000 символов (`422` проверки запроса) | Сообщение с лимитом: «Вакансия длиннее 20 000 символов — оставьте требования и стек» / «Ответ длиннее 5 000 символов — сократите» |
| Бот добавлен в группу | «Я работаю только в личных сообщениях», дальше ничего |
| Telegram недоступен (сеть, VPN моргнул — на живой проверке пропал на 5 минут сразу после генерации вопросов) | Отправка и правка повторяются через 1, 3 и 10 с, флуд-лимит — через сколько просит Telegram. Сессия сохраняется в состоянии до отправки, поэтому `/train` продолжает её, а не генерирует заново. Не доставленная оценка не держит пользователя в «жду оценку»: следующий вопрос всё равно задаётся |
| Обрывок вакансии («Ключевые навыки: …») принимается за вакансию, модель додумывает требования | Не правится в спринте 6: после склейки частей случается редко. Строже отказ «не вакансия» — спринт 10 |

**Ссылки за VPN с fake-IP.** VPN-клиенты в режиме fake-IP (Clash, sing-box и т. п.) отдают на любое имя
адрес из зарезервированного диапазона (`198.18.0.0/15`, `240.0.0.0/4`), а настоящий адрес знает только VPN.
Защита от SSRF (002) такие адреса отклоняет, и ни одна ссылка не открывается. В API появляется
`FETCH_ALLOW_NETWORKS` — список подсетей через запятую, которые считаются внешними (по умолчанию пусто,
защита не ослаблена). Если ссылка отклонена из-за адреса в диапазонах fake-IP, в лог API пишется подсказка
про `FETCH_ALLOW_NETWORKS`. `FETCH_ALLOW_PRIVATE=true` по-прежнему открывает всё — только для экспериментов.

## 5. API: токены и служебные эндпоинты

### 5.1. Сервисный токен (BOT-3)

- `API_SERVICE_TOKEN` (env). Задан → все `/api/v1/*`, кроме `/health` и `/health/llm`, требуют
  `Authorization: Bearer <token>`; без него или с неверным — `401 unauthorized`. Сравнение — `hmac.compare_digest`.
- Пусто → проверки нет, при старте API пишет `WARNING service token not set`.
- Бот и `research/*/check.py` берут токен из того же env. Токен не логируется (`SecretStr`).

### 5.2. Админ-токен и служебные эндпоинты (000 §8)

- `ADMIN_TOKEN` (env). Не задан → `/api/v1/admin/*` отвечают `404` (выключены). Задан → требуется
  `Authorization: Bearer <admin token>`, иначе `401`. Сервисный токен к админским путям не подходит.
- Эндпоинты — тонкие обёртки над теми же функциями, что у `sobesnik-cli` (`create_run`, `get_run`,
  `import_dataset`, `list_datasets`, `select_rows` + `write_csv`). Логика в CLI и HTTP одна.

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `GET /admin/datasets` | — | `200 [{name, items, license, lang, …}]` как `dataset list` |
| `POST /admin/datasets` | multipart: `file` (JSONL), `name?`, `sample?`, `seed?` | `201 {dataset, questions, answers}`; `409` имя занято; `422` ошибка формата; голосовые строки — `422 voice_dataset_cli_only` |
| `POST /admin/eval-runs` | `{name, model?, dataset?, session_id?, user_id?, since?, until?, rubric?, prompt?, temperature?, seed?, transcript?}` | `202 {id, status, total, …}`; задача ставится в очередь |
| `GET /admin/eval-runs/{id}` | — | `200 {id, name, model, status, total, done, failed, error, …}`; `404` |
| `POST /admin/eval-runs/{id}/restart` | — | `202`, готовые оценки пропускаются (как `eval-run restart`) |
| `GET /admin/evaluations.csv` | query: `run` (повторяемый), `live`, `session`, `dataset`, `format=wide\|long` | `200 text/csv`, `Content-Disposition: attachment` |

Фильтра выгрузки «модель» и «период» (000 §8) у CLI нет — в HTTP их тоже нет: модель и период задаются
прогоном (`run`). Если понадобятся — добавятся в `ExportFilter`, и в CLI, и в HTTP сразу.

## 6. События статуса ответа (ANS-3)

### 6.1. Формат

- Stream `sobesnik:answer-events`, `XADD … MAXLEN ~ 10000` (старые события обрезаются).
- Поля: `answer_id`, `status` (`transcribing|evaluating|done|failed`), `error` (пусто или код), `kind`
  (`text|voice`), `session_id`, `user_id`. Ни текста ответа, ни транскрипта, ни оценки — бот берёт их
  `GET /answers/{id}`, событие только будит его.
- Публикуются только ответы пользователей (`source = user`): у ответов датасета нет получателя,
  а прогон на сотни ответов зря забил бы Stream.

### 6.2. Публикация

- Интерфейс в `apps/api`:
  ```python
  class AnswerEvents(Protocol):
      async def publish(self, answer: Answer) -> None: ...
  ```
  `RedisAnswerEvents` (XADD) и `NullAnswerEvents`; тесты подставляют `RecordingAnswerEvents`.
- Публикует воркер **после коммита** каждой смены статуса в `process_transcription` и `process_answer`
  (включая `_fail`). Внутри — хелпер `_set_status(db, deps, answer, status, error)`: commit, затем publish.
- Публикация — best effort: ошибка Redis пишется в лог (`answer_id`, тип ошибки) и не валит задачу.
  Потерянное событие бот всё равно увидит при сверке (§6.3).
- `received` не публикуется: о нём бот знает из ответа `202`.

### 6.3. Чтение в боте

- Группа потребителей `bot`, потребитель — имя хоста контейнера. `XGROUP CREATE … $ MKSTREAM` при старте
  (группа уже есть — не ошибка).
- Цикл: сначала дочитать свои неподтверждённые (`XREADGROUP … 0`), потом новые (`>` с `BLOCK 5000`).
  Обработка события: найти ожидающий ответ в состоянии бота (§7.3) — нет, значит событие чужое или старое:
  `XACK` и дальше. Есть — `GET /answers/{id}`, отрисовать (§4.5, §8), `XACK`.
- **Сверка при старте и раз в 60 с:** для каждого ожидающего ответа старше 60 с без событий — `GET /answers/{id}`.
  Если он уже `done`/`failed` — обработать как событие. Это страховка от потерянного события, а не опрос
  как основной путь (000 §12).
- Обработка идемпотентна: повторное событие того же статуса не меняет сообщение второй раз.

### 7.1. Пакет `apps/bot`

```
apps/bot/src/sobesnik_bot/
  __main__.py     запуск: python -m sobesnik_bot, сборка диспетчера
  settings.py     BotSettings из env
  api.py          ApiClient (httpx) и протокол Api для тестов; свои модели ответов
  flow.py         Trainer: сценарий тренировки, индикатор «печатает…», сверка ожидающих ответов
  handlers.py     команды, сообщения и кнопки → Trainer
  render.py       профиль, вопрос, статус, оценка, сводка → текст и клавиатуры (чистые функции)
  events.py       чтение Stream группой потребителей
  state.py        состояние пользователя и ожидающие ответы в Redis
  access.py       allowlist (middleware)
  logs.py         JSON-логи, токен вырезается
```

- Зависит только от `aiogram`, `httpx`, `redis` и `pydantic-settings`. **Не импортирует `sobesnik_api`**
  (apps не зависят друг от друга, CLAUDE.md): модели ответов API — свои, минимальные, с `extra="ignore"`.
- Ошибки API → `ApiError(status, code, message)`; таймаут — 150 с (с запасом над `LLM_TIMEOUT_S = 120`),
  сеть до API недоступна — `ApiUnavailable`.
- Режим разметки — HTML (экранирование через `html.escape`): текст вопросов и ответов модели может содержать
  `*`, `_` и обратные кавычки, которые ломают Markdown.

### 7.2. Индикатор «печатает…»

`async with trainer.typing(chat_id):` — фоновая задача шлёт `sendChatAction(typing)` каждые 4 с, снимается при
выходе. Для ожидающего ответа индикатор живёт в задаче, привязанной к `answer_id`, и отменяется финальным
событием или через 15 мин. После перезапуска бота индикаторы восстанавливаются для ожидающих ответов.

### 7.3. Состояние

Redis, база `REDIS_URL` бота (по умолчанию та же Redis, отдельный префикс `bot:`):
- `bot:user:{telegram_id}` — hash: `user_id`, `vacancy_id`, `session_id`, `question_id` (ждём ответа на него),
  `mode` (`idle|vacancy|answer`).
- `bot:pending:{answer_id}` — hash: `chat_id`, `status_message_id`, `kind`, `session_id`, `question_id`,
  `last_status`, `accepted_at`. Удаляется после финального события. TTL 1 сутки — на случай забытого.
- Состояние — только идентификаторы. Текстов ответов, транскриптов и аудио в Redis бота нет.
- Потеряли состояние (Redis без тома, новый Redis) — бот предлагает прислать вакансию заново. Чтобы такого
  не было в обычной жизни, у Redis в compose появляется том и `--appendonly yes` (§3 п. 5).

Aiogram FSM не используется: состояние нужно и обработчикам, и циклу событий, а hash по id проще.

### 7.4. Доступ (BOT-5)

`BOT_ALLOWED_IDS` — список `telegram_id` через запятую. Пусто — бот открыт всем. Не в списке — один ответ
«Это закрытый инстанс Sobesnik» на любое сообщение, в API ничего не уходит. В лог — только факт отказа и id.

### 7.5. Токен и логи

- `TELEGRAM_BOT_TOKEN` — только в `.env` (в git не попадает), `SecretStr`. В `.env.example` — пустая строка.
- Токен входит в URL запросов к Telegram, поэтому: логгеры `aiogram.client`/`aiohttp` не ниже `WARNING`, плюс
  фильтр логов, который заменяет токен на `***` в любой строке. Тест: запись с токеном в лог выходит без него.
- Токен не задан → бот пишет «TELEGRAM_BOT_TOKEN не задан, бот не запущен» и выходит с кодом 0
  (`restart: on-failure`): `docker compose up` без токена работает, как раньше.
- Логи бота — JSON, как у API: `telegram_id`, `answer_id`, команда, статус, задержка. Без текстов сообщений,
  вакансий, ответов и без аудио.

  command: ["python", "-m", "sobesnik_bot"]

## 8. Что видит пользователь

### 8.1. Принцип

Research показал: абсолютный балл `qwen3.5:4b` надо читать с допуском ±20, порядок (лучше/хуже) надёжнее числа,
а из сомнений в распознавании полезна треть. Поэтому бот:
- ведёт словом, а не числом, и не показывает точность, которой нет;
- выносит наверх то, на что можно действовать: упущенные пункты и совет;
- подаёт сомнения в распознавании как «проверьте сами», а не как факт.

### 8.2. Оценка

Вариант А (рекомендуемый, §14 вопрос 1):

> 🟡 **Средне** · ≈ 65 из 100
> Корректность ●●○ · Полнота ●○○ · Глубина ●○○ · Термины ●●○ · Структура ●●●
>
> **Что упущено:**
> • GIL не мешает I/O-задачам
> • отличие корутины от потока
>
> **Совет:** начните с определения event loop, потом — пример с `gather`.
>
> [Почему такие баллы?]

- Слово по итогу и признаку «пройден» (считает API): не пройден — 🔴 «Слабо»; пройден и итог < 75 —
  🟡 «Средне»; ≥ 75 — 🟢 «Хорошо». Порог 75 — константа в `render.py` (только отображение).
- Число — «≈ N», округлённое до 5. При первой оценке в сессии — строка мелким шрифтом:
  «Балл примерный, ±20: модель небольшая. Ориентируйтесь на упущенное и совет».
- Критерии — точками 0–3, без весов. Обоснования критериев — по кнопке «Почему такие баллы?» (отдельным
  сообщением, `GET /answers/{id}`), чтобы не заваливать чат.
- Модель и версии промпта/рубрики пользователю не показываются (они есть в CSV для исследователя).

Вариант Б — только слово и точки, число скрыто совсем.

## 9. Генерация вопросов: синхронно (решение из спринта 3)

Остаётся **синхронной** в `POST /sessions`: ~40 с при таймауте LLM 120 с и таймауте бота 150 с. В боте это
переносимо: статус «Готовлю вопросы… обычно около 40 с» и индикатор. Перенос в воркер потребовал бы статусов
сессии, второго вида событий и ожидания в боте — ради выигрыша, которого пользователь не почувствует: ждать
вопросы ему всё равно надо.

Правило пересмотра: если в живой проверке (§12) разбор + генерация дольше 120 с или упираются в таймаут —
перенос в воркер уходит в спринт 10, а в «Итоги» записывается замер. Вариант переноса — генерация пачками,
разобрана в §16.1.

Без Telegram, без Ollama, без сети.

**API:**
- сервисный токен: задан — без заголовка `401`, с неверным `401`, с верным `200`; `/health*` без токена;
  не задан — всё как раньше;
- админ-токен: не задан — `404`; сервисный токен к `/admin/*` — `401`; верный — работает;
- `/admin/datasets`: импорт маленького JSONL, `409` на повтор, `422` на голосовой; список;
- `/admin/eval-runs`: создание ставит задачу (`FakeQueue`), статус, restart; `/admin/evaluations.csv` —
  те же колонки, что у CLI, на тех же данных.

**Воркер и события:**
- `RecordingAnswerEvents`: текстовый ответ даёт `evaluating → done`; голосовой — `transcribing → evaluating →
  done`; `asr_empty`, `audio_missing`, `llm_bad_output`, последняя попытка `llm_unavailable` — `failed`
  с кодом; ответ датасета — ни одного события;
- ошибка публикации не валит задачу, статус в БД верный;
- `RedisAnswerEvents` против Redis из compose: `XADD` и чтение группой (как Postgres в тестах API).

**Бот** (`apps/bot/tests`): API — `FakeApi` через протокол `Api`; Telegram — фейковая сессия `Bot`, которая
записывает вызовы методов и отдаёт заготовленные ответы; апдейты подаются через `Dispatcher.feed_update`.
- `/start` создаёт пользователя; вакансия текстом и ссылкой; кнопка уровня шлёт `PATCH`;
- тренировка: вопрос → текст → `202` → статус «Оцениваю»; событие `done` → оценка → следующий вопрос;
  последний → `finish` → сводка; «Пропустить»;
- голос: скачивание в память и multipart в API; событие `evaluating` → расшифровка в статусе; `asr_empty` →
  просьба повторить; ошибки `422`/`413`/`503` → тексты;
- 60 с без событий → «думает дольше обычного» (время подменяется);
- сверка: потерянное событие подхватывается `GET /answers/{id}`; повтор события не дублирует сообщение;
- allowlist: чужой id — отказ и ни одного вызова API;
- `render.py`: слово и «≈ N» по итогу и `passed`, точки критериев, обрезка расшифровки, ≤ 3 сомнения,
  экранирование HTML, таблица ошибок;
- фильтр логов вырезает токен.

## 12. Быстрая живая проверка

Мак 16 ГБ, `qwen3.5:4b`, whisper `small`. Один проход, без замеров «на точность»:
1. `docker compose up -d --build`, токен бота и свой `telegram_id` в `.env` (автор).
2. Автор в Telegram: `/start` → вакансия (ссылка hh.ru) → смена уровня → тренировка из 3 вопросов
   (`/train 3`) → ответ текстом → ответ голосом (~30 с) → пропуск третьего → сводка.
3. Claude параллельно смотрит логи `api`, `worker`, `bot`: время разбора, генерации, оценки; что в логах нет
   токена, текстов и аудио.
4. Перезапуск бота, пока голосовой ответ в обработке, — результат приходит после старта.
5. `ollama stop qwen3.5:4b`.

В «Итоги» — таблица времени (разбор, генерация 3 вопросов, оценка текста, голос от отправки до оценки) и что
выяснилось.

## 13. Критерии приёмки

1. С1–С3 проходятся в Telegram на реальной вакансии без ручного вмешательства (живая проверка §12).
2. Приём ответа подтверждается ≤ 2 с (BOT-4); результат приходит событием, статус «распознаю → оцениваю»

Пожелания с живой проверки, которые не входят в спринт 6.

**Подробный разбор с источниками.** Сейчас оценка — пункты, которые упущены, и совет одной-двумя фразами

- Число вопросов: уже есть — кнопки 5 / 10 / 15 и `/train N` (3…15), §4.3.

- Только обязательные требования вакансии, сложность (проще / как в вакансии / сложнее) — спринт 10.

### 16.1. Генерация пачками

**Идея.** Сейчас `POST /sessions` ждёт все N вопросов одним вызовом модели: 5 вопросов ~30 с, 15 — до 2 мин.
Вместо этого API генерирует синхронно только первую пачку (2 вопроса, ~13 с: 3 вопроса на живой проверке
002 — 18 с), отдаёт сессию, а остальные вопросы дописывает воркер пачками по 2–3, пока человек отвечает.
Первый вопрос приходит в 2–3 раза быстрее, длинная тренировка не упирается в таймаут.

**Почему ложится на текущий код.** План слотов (`plan_questions`: какое требование и тема у вопроса i)
уже строится сразу на все N до вызова модели, а защита от повторов (`asked` + `question_problems`) уже
сравнивает новые вопросы с заданными раньше. Пачка — это тот же вызов для слотов `[i:j]`, где в `asked`
добавлены вопросы прошлых пачек этой сессии.

**Как:**
- План слотов сохраняется в сессии (`session.plan` JSON, `questions_total = N`), сессия получает поле
  `generation`: `ready` | `generating` | `partial` (часть пачек не удалась).
- `POST /sessions` → план + первая пачка синхронно → `201` с вопросами 1–2 и `questions_total` → задача
  `generate_batch(session_id)` в очередь.
- Задача берёт **первый пустой слот** по плану, генерирует пачку, пишет её одной транзакцией, ставит
  следующую задачу. Одна пачка — одна задача: оценка ответа ждёт в очереди не дольше одной пачки (~15 с),
  а не всей генерации.
- Событие `questions_ready {session_id, ready: 4}` в тот же Redis Stream (поле `kind=session`) — бот
  узнаёт, что вопрос появился.
- В боте: вопрос `i` ещё не готов → «🧩 Готовлю следующий вопрос…» и ожидание события, со сверкой раз в
  30 с, как у ответов.

**Гонки, дубли, идемпотентность:**

| Риск | Что происходит | Защита |
|---|---|---|
| Задача выполнилась дважды (arq повторил после таймаута, воркер упал после записи) | Два набора вопросов на одни позиции | Уникальный индекс `session_question (session_id, position)` (сейчас его нет — добавить миграцией); вставка `ON CONFLICT DO NOTHING`; задача ставится с `_job_id = gen:{session}:{position}` — arq не возьмёт вторую такую же. Повтор находит слоты занятыми и выходит |
| Две пачки параллельно (`worker_max_jobs > 1`) | Обе берут один «первый пустой слот» | Задача берёт `SELECT … FOR UPDATE` строку сессии — пачки одной сессии идут строго по очереди; при `job_id` по позиции это и так одна задача на позицию |
| Повтор темы между пачками | Модель не видит вопросы соседней пачки | Вопросы прошлых пачек сессии идут в `asked`, `question_problems` отклоняет похожие, генерация повторяется (`max_retries`). Порядок пачек строгий, поэтому «соседних» незаписанных пачек не бывает |
| Человек ответил на 2 вопроса быстрее, чем готова пачка | Вопроса 3 ещё нет | Бот ждёт событие (выше). API на ответ к несуществующей позиции — уже `404 question_not_in_session` |
| `/finish` или «Пропустить всё», пока генерация идёт | Задача дописывает вопросы в закрытую сессию | Задача под блокировкой проверяет `status == active`, иначе выходит без записи; сводка считает только заданные вопросы |
| Модель недоступна на второй пачке | Сессия «застряла» на 2 вопросах из 10 | После повторов arq — `generation = partial`, событие; бот: «Подготовил только 4 вопроса из 10 — закончим на них?» с кнопками «Закончить» / «Попробовать ещё» (ставит задачу заново с того же слота) |
| Перезапуск бота или API посреди генерации | Задача в Redis, состояние в БД | Ничего не теряется: задача в очереди arq, план и готовые вопросы в БД, бот сверяется по `GET /sessions/{id}` |
| Один Ollama и `worker_max_jobs = 1` на Маке | Оценка ответа 1 ждёт, пока модель пишет пачку | Мелкие пачки (одна задача ≈ 15 с) — оценка задерживается на одну пачку. Это главная цена: ответ на вопрос 1 оценивается на ~15 с дольше. Если мешает — пачку ставить, только когда в очереди нет оценок |

**Цена.** Миграция (план, статус генерации, уникальный индекс), задача воркера, второй вид события, ожидание
в боте, ~15 тестов на гонки. Это переделка контракта `POST /sessions`, поэтому — отдельная спека.
Место: спринт 10 (или раньше, если 15 вопросов начнут упираться в таймаут). До тех пор действует §9.
